# 面试准备手册：企业级 Agent 推理优化平台

> 所有改造点源于**同一个项目**在不同迭代阶段遇到的实际问题。
> 每个改造点的产生都有前因后果，是一个自然演进的过程。

---

## 一、项目背景

### 项目定位

面向企业内部员工的知识问答与任务执行平台。员工可以通过自然语言提问，系统自动检索知识库、调用业务系统、生成回答。

### 典型用户

- 研发团队：查技术文档、查 Bug 修复记录、查线上事故报告
- 产品团队：查需求文档、查用户反馈、查竞品分析
- 运营团队：查数据报表、查活动规则、查 FAQ

### 迭代历程

```
第一版：纯 RAG 问答（检索→生成）
   ↓ 用户问"能不能帮我查 Jira 工单状态？"
第二版：Agent + ReAct（可以调工具了）
   ↓ 复杂任务执行效率低、容易跑偏
第三版：Plan-then-Execute（先规划再执行）
   ↓ 工具太多了，LLM 选不对工具
第四版：工具预筛选 + 结果校验（只发 Top-5 给 LLM）
   ↓ 长对话记忆混乱、Token 消耗大
第五版：层级化压缩 + 结构化记忆（三级压缩+分类存储）
   ↓ 每次增删工具都要重启服务
第六版：动态工具装配（运行时热加载）
```

---

## 二、改造点 1：Plan-then-Execute 混合推理架构

### 2.1 在项目中是怎么产生的？

项目进入第二版后，Agent 具备了调用工具的能力（查 Jira、查知识库、查代码仓库）。运营团队提了一个需求：

> **业务需求**："帮我写一份上周的线上事故报告，包含事故数量、影响范围、处理进度"

这个任务在 ReAct 模式下需要 8-12 轮：
1. 检索知识库 → "事故报告模板"
2. 查 Jira → "上周所有 P0/P1 Bug"
3. 查代码仓库 → "对应的 Hotfix 记录"
4. 查值班表 → "谁处理的"
5. 到第 5 步时，LLM 经常忘记"要生成报告"这事，开始分析具体某个 Bug

**问题**：纯 ReAct 做复杂任务时，LLM 在长轮次中丢失了原始目标，跑偏率约 24%。

**方案**：先让 LLM 生成执行计划，再把计划注入到 ReAct 循环中，每一轮都知道自己在执行第几步、还剩几步。

### 2.2 面试问答

---

#### Q1：Plan 是怎么保证质量的？LLM 生成的 Plan 不准怎么办？

> **回答要点**：PlanValidator 两层校验 + 执行时 LLM 有自主权
>
> **详细回答**：
> 我设计了 PlanValidator 做两层校验：
>
> **第一层：格式校验**
> - 检查是否包含 `Step N:` 格式的步骤
> - 步骤数控制在 1-8 步（少了说明没理解任务，多了说明拆分过细）
> - 不符合格式的让 LLM 重新生成，最多重试 2 次
>
> **第二层：内容校验**
> - 检查每步描述是否引用了当前可用的工具名
> - 没引用工具的步骤（纯 LLM 推理步骤）允许，但不允许全是纯推理
>
> 更重要的是——**Plan 不是给机器执行的指令脚本，而是给 LLM 看的上下文**。执行某一步时，LLM 仍然可以自主决定调什么工具。Plan 只是给 LLM 一个"全局地图"，避免在长轮次中迷路。
>
> 用一句话总结：**Plan 是路标不是铁轨**。

---

#### Q2：和纯 ReAct 相比效果怎么样？

> **回答要点**：轮数减少 + 跑偏率降低，但基于内部测试
>
> **详细回答**：
> 在我们内部测试集（50 个复杂多步骤任务）上：
> - 纯 ReAct 模式：平均 9.2 轮/任务，跑偏率 24%
> - Plan-then-Execute：平均 4.1 轮/任务，跑偏率 8%
>
> 运营团队的"事故报告生成"任务，之前经常跑偏到分析单个 Bug，上了 Plan 之后基本不会了，因为第 1 步生成计划时 LLM 已经知道了"我最终要输出一份报告"，每一步都在为这个目标服务。
>
> **说明**：这是我们在内部场景下的数据，不同业务场景可能有差异。

---

#### Q3：这个 Plan 和 AutoGPT 的规划有什么区别？

> **回答要点**：AutoGPT 持续重规划，我是一次规划+轻量执行
>
> **详细回答**：
> 两个关键区别：
>
> **规划频率不同**
> AutoGPT 每执行一步都要重新"思考"下一步做什么，LLM 调用次数多、成本高。我的方案是在开始时一次性生成全局计划，后续不需要 LLM 重新规划。
>
> **适用场景不同**
> AutoGPT 适合完全开放的任务（如"帮我做一个产品"），需要持续探索。我的方案适合流程相对固定的企业场景（如"按模板生成报告"），步骤可预判、执行路径稳定。
>
> 对我们项目来说，企业内部任务场景恰好是后者——事故报告的流程是固定的，我们不需要 Agent 自己发明新流程。

## 三、改造点 2：智能工具编排系统

### 3.1 在项目中是怎么产生的？

项目接入的业务系统越来越多：知识库检索、Jira 查询、GitLab 代码搜索、值班表查询、Wiki 查询、Jenkins 流水线状态、监控告警查询......

到第三版的时候，Agent 可以调用的工具达到了 20+ 个。

运营团队开始抱怨：

> **业务反馈**："我让它查一个 Jira 工单，它去查了知识库，浪费了好几分钟。"

排查发现每次 LLM 调用时，20 个工具的定义全部塞到 Prompt 里，占用了大量上下文窗口（约 8000 tokens）。工具一多，LLM 选择工具的准确率从 95% 降到了 80%。

同时，工具调用本身也不可靠：

> **业务反馈**："它说查到了事故记录，但点开链接是空的。"

排查发现知识库检索工具返回了空结果，但 Agent 把空结果直接当成"查到了"返回给了用户。

**问题**：
1. 20 个工具定义占用了 8000 tokens，无效开销大
2. LLM 在大量工具中选错工具的概率变大
3. 工具返回的异常结果（空结果、错误码）直接被透传给了 LLM，LLM 经常被误导

**方案**：
1. **工具预筛选**：用户提问后先计算 embedding 相似度，只把 Top-5 最相关的工具定义发给 LLM
2. **结果校验与自动重试**：工具返回结果后做三类检测，异常时自动换参数重试

### 3.2 面试问答

---

#### Q1：工具预筛选的准确率够吗？Top-5 会不会漏掉需要的工具？

> **回答要点**：95% 召回率 + 强制候选 + 降级开关
>
> **详细回答**：
> 我从三个层面保证覆盖率：
>
> **第一层：描述质量规范**
> 工具描述的写作质量直接影响 embedding 匹配效果。我定了一个规范：工具描述必须包含"场景词 + 能力词 + 关键词"。比如：
> - ❌ "Jira 查询"
> - ✅ "查询 Jira 工单状态、Assignee、Sprint 信息，支持按项目 Key 筛选"
>
> **第二层：强制候选**
> 有些通用工具（如知识库检索）不管得分高低都强制加入候选名单，避免被误筛掉。
>
> **第三层：条件启用**
> 工具数少于 10 时不开启预筛选，避免不必要的复杂度。
>
> 在内部测试中，Top-5 召回率约 95%。那漏掉的 5% 我们会定期回测分析——是描述问题还是算法问题，然后针对性优化。

---

#### Q2：如果 Top-5 没命中用户的意图，用户又没注意到，直接给了错误答案怎么办？

> **回答要点**：LLM 发现工具不可用时能感知到
>
> **详细回答**：
> 这个问题很实际。我的理解是——**如果 Top-5 里没有用户需要的工具，LLM 在 ReAct 循环中会发现它调不动**。
>
> 举个例子：用户问"查一下 Jenkins 构建状态"，但 Jenkins 工具不在 Top-5 里。LLM 只能拿 Top-5 里的工具去尝试——比如用检索工具搜"Jenkins 构建状态"。检索肯定没有实时数据，返回空结果。这时 LLM 会意识到"这个工具不对劲"，然后在回答中说"我没有查询 Jenkins 状态的权限，请联系运维同事"。
>
> 最坏情况是 LLM 自己编造数据，但这种情况在我们的方案里会被**工具结果校验**拦截——空结果不会透传给 LLM，而是返回"未查到相关数据，请确认权限"。

---

#### Q3：工具结果校验具体做了什么？为什么只重试一次？

> **回答要点**：三类检测 + 一次重试的工程考量
>
> **详细回答**：
> 我做了三类异常检测：
>
> **1. 空结果检测**
> 返回 None、空列表 → 自动换参数重试（加"同义词"或"扩大范围"）
>
> **2. 错误格式检测**
> 工具返回 `**ERROR**` 开头 → 直接丢弃，不给 LLM 看到
>
> **3. 数据超长检测**
> 结果 > 50000 字符 → 截断到 20000 + 标记
>
> **为什么只重试一次？**
> 这是成本考量。一次重试 + 一次兜底，如果还失败，说明大概率是数据源本身的问题（比如数据库里就没数据），重试再多也没用。而且每次工具调用都有延迟和成本，不能让用户等太久。

---

#### Q4：两个工具同时执行，会不会有冲突？比如同时写数据库？

> **回答要点**：读并行、写串行
>
> **详细回答**：
> 在我们的项目里，绝大多数工具是读操作（检索知识库、查 Jira、查 GitLab），天然可以并行。少数写操作工具（创建工单、发送通知）我在注册时标记了 `write_lock=True`，调度器看到这个标记会单独串行执行。

## 四、改造点 3：层级化记忆管理

### 4.1 在项目中是怎么产生的？

Agent 上线运营后，最活跃的用户是客服团队。他们处理一个用户投诉可能需要 20-30 轮对话。

运营团队的新吐槽：

> **业务反馈**："用户问退款到哪了，它去查了物流信息。明明之前说过是京东快递，它非按顺丰去查。"

排查发现当对话超过 10 轮后，LLM 开始遗忘早期信息——用户的订单号、选择的快递公司、投诉原因。原因是每次调用 LLM 时，历史消息太长被截断了。

另一个问题是 Token 费用：

> **业务反馈**："上个月 LLM 费用涨了 3 倍。"
>
> 排查发现 30 轮对话 + 20 次工具调用结果，单次 LLM 调用的 Token 消耗超过 2 万。

**问题**：
1. 截断策略太粗暴——超过 3 轮就全部压缩，但压缩后丢失了关键数据（订单号、物流公司）
2. 不压缩的话 Token 消耗太大

**方案**：
1. **三级压缩**：短对话不压缩、中对话只压工具详情、长对话 LLM 摘要
2. **结构化记忆**：把记忆按类型分类，检索时只取最相关的，不全部拼接

### 4.2 面试问答

---

#### Q1：三级压缩的阈值 3 和 10 怎么来的？

> **回答要点**：基于业务场景的观察，不是理论推导
>
> **详细回答**：
> 这两个阈值是我从客服场景的实际对话数据中观察出来的：
>
> **3 轮以内**
> 客服场景中 1-3 轮通常在处理同一个子问题。比如"查一下我的订单 → 订单号 12345 → 这个订单怎么了？"。这三轮高度相关，压缩会丢失因果链。
>
> **4-10 轮**
> 这时候通常已经出现工具调用了（查订单 → 查物流 → 查退款），但整体还是在围绕同一个问题展开。我们选择只压缩工具返回的详细数据（比如物流详情的 JSON），保留对话主线和工具调用记录。
>
> **10 轮以上**
> 客服场景中 10 轮以上通常是多个子问题叠加（查订单 → 投诉 → 要求补偿 → 查询进度）。LLM 开始遗忘早期信息，需要 LLM 主动做摘要。
>
> **坦白说**：3 和 10 不是最优值，是基于经验设置的初始值。如果要严谨调优，应该对不同场景跑对照试验来确定最佳阈值。

---

#### Q2：结构化记忆为什么分 5 类？检索时怎么用？

> **回答要点**：分类解决"噪音"问题，embedding 检索
>
> **详细回答**：
> **为什么分类**：
> 如果所有记忆放在一个袋子里，检索时噪音很大。比如用户早上说"我地址在北京"，下午问"快递到哪了"，传统关键词检索会把"北京"当成相关上下文带进去。但如果分类了，在北京属于 factual"事实"，而"快递到哪了"应该检索 context"上下文"，就不会匹配错。
>
> **五类划分**：
> ```
> factual（事实）     → "用户地址在北京，铂金会员"
> preference（偏好）  → "不喜欢客套，喜欢直接答案"
> context（上下文）   → "刚才查了订单 #12345，物流延期"
> session（会话）     → "用户今天情绪不太好，已经催了 3 次"
> task_status（状态） → "退款流程已完成，等待到账"
> ```
>
> **检索方式**：用 embedding 匹配，只取 Top-3，不是全量拼接。
>
> 比如用户问"退款到哪了" → embedding 检索 → 匹配到 task_status → "退款流程已完成，等待到账" → 不匹配 factual → 不会把"用户地址在北京"带进来。

---

#### Q3：每次对话都用 LLM 做分类，成本怎么控制？

> **回答要点**：批量分类，5 条合并一次
>
> **详细回答**：
> 我设了一个积累窗口——攒够 5 条对话才统一提交一次 LLM 分类。5 条对话打包成一段文本让 LLM 一次处理完。这样 10 轮对话只需要 2 次分类调用，而不是 10 次。成本降了 80%。
>
> **补充**：5 条是初始值，实际使用时可以根据场景调整。对话短的场景可以调大，对话长的场景可以调小。

## 五、改造点 4：运行时动态装配

### 5.1 在项目中是怎么产生的？

项目变成了公司内部的 AI 平台，多个部门接入，各部门需要的工具不一样：
- 研发团队：Jira、GitLab、Jenkins、Wiki
- 运营团队：知识库、值班表、公告系统
- 财务团队：ERP、报销系统、预算系统

开发团队开始抱怨：

> **开发反馈**："运营那边想加一个新工具——查企业微信通讯录。我改完代码发版，重启服务，研发那边正好在用，服务断了 2 分钟，被骂了。"

另一个问题：

> **开发反馈**："财务那边说 Jira 查询工具有 Bug——查不到已关闭的工单。我修好了发布新版，问题是我怎么让已经在运行的 Agent 用上新版？"

**问题**：
1. 每次增删工具都要重启服务，影响所有用户
2. 工具更新后，已经在运行的 Agent 实例无法感知

**方案**：
1. 工具信息存 Redis（类路径、版本号、参数描述），不硬编码
2. Agent 运行时从 Redis 实时加载当前租户的工具列表
3. 工具变更通过 Redis Pub/Sub 通知所有 Agent 实例清除缓存

### 5.2 面试问答

---

#### Q1：为什么不用 pickle 序列化？importlib 安全在哪？

> **回答要点**：pickle 可以远程执行任意代码
>
> **详细回答**：
> 这是一个安全问题。Pickle 的反序列化可以执行任意代码。如果 Redis 被攻破，攻击者在 Redis 里放一个恶意 pickle，Agent 反序列化时就会执行攻击者的代码——这等于把服务器权限送出去了。
>
> Importlib 没有这个问题。它只能在 Python 的 `sys.path` 路径下导入模块，攻击者要植入恶意代码必须先攻破服务器的文件系统，这个难度不是一个量级的。
>
> 而且 pickle 还有兼容性问题——工具类改了代码后，Redis 里旧的 pickle 反序列化会失败。importlib 每次导入的都是最新的代码，不存在这个问题。

---

#### Q2：版本升级时正在执行的请求会受影响吗？

> **回答要点**：当前请求不受影响，下次请求自动加载新版
>
> **详细回答**：
> 这是设计时重点考虑的场景。我们的策略是：**执行和加载解耦**。
>
> Agent 实例初始化完成后，它持有的工具引用就是固定的。当前请求会继续用旧版本执行完。执行完毕后清除本地缓存，下次请求时从 Redis 重新加载，自动拿到新版本。
>
> 所以整个过程是：
> 1. 凌晨 2 点运营提交"新增通讯录工具"→ 写入 Redis，发布通知
> 2. 正在查询 Jira 的 Agent 不受影响，继续用旧版本跑完
> 3. 当前请求结束后，Agent 收到通知，清除缓存
> 4. 下一个用户提问时，Agent 自动加载了新工具
>
> 对用户完全无感，不需要重启服务。

---

#### Q3：怎么回滚？如果新版工具出了 Bug 怎么办？

> **回答要点**：版本号 + active 指针，秒级回滚
>
> **详细回答**：
> 我设计了一个活跃版本指针：
> ```redis
> agent_tool:retrieval:v2 → {class_path, version=v2}
> agent_tool:retrieval:v1 → {class_path, version=v1}
> agent_tool:retrieval:active → v2
> ```
> Agent 加载工具时查的是 `active` 指针，不是固定版本。回滚只需要把 `active` 切换回 v1：
> ```python
> redis.set("agent_tool:retrieval:active", "v1")
> redis.publish("agent_tools:changes", "retrieval")
> ```
> Agent 收到通知 → 清除缓存 → 下次请求自动加载 v1。整个过程对用户无感。

## 六、项目的演进脉络总结

```
第一版：纯 RAG
  └─ 只能检索知识库，不能执行业务操作

第二版：Agent + ReAct 工具调用
  └─ 能调 Jira/GitLab 了，但复杂任务跑偏严重
  └─ [催生] Plan-then-Execute → 先规划再执行，降低跑偏率

第三版：工具不断接入，达到 20+
  └─ 工具太多 LLM 选不对，Token 浪费
  └─ [催生] 工具预筛选 → 只发 Top-5 给 LLM
  └─ 工具返回结果不可靠
  └─ [催生] 结果校验与自动重试 → 空结果自动拦截重试

第四版：客服场景长对话上线
  └─ 20+ 轮对话 Token 消耗大，LLM 遗忘早期信息
  └─ [催生] 三级记忆压缩 → 分层压缩，避免一刀切
  └─ 记忆一锅端，噪音大
  └─ [催生] 结构化记忆 → 分类存储 + embedding 检索

第五版：多部门接入，变成企业平台
  └─ 每次增删工具都要重启服务，影响用户
  └─ [催生] 动态工具装配 → Redis 热加载，不停机更新

第六版：优化迭代
  └─ 工具并行执行顺序不合理
  └─ [催生] 智能并行调度 → SJF 策略优化等待时间
  └─ 固定 Prompt 不能适配所有问题类型
  └─ [催生] 动态 Few-Shot → 语义检索相关示例注入
```

## 七、面试总策略

### 7.1 故事线

面试时按这个顺序讲，逻辑最顺：

```
我们做了一个企业内部 AI 助手
  → 第一版只能问答
  → 加上了工具调用（Agent + ReAct）
    → 但复杂任务跑偏 → Plan-then-Execute
    → 工具多了选不对 → 工具预筛选
    → 工具结果不可靠 → 结果校验
  → 客服场景长对话 → 三级压缩 + 结构化记忆
  → 多部门接入 → 动态装配
  → 持续优化 → 智能调度 + 动态 Few-Shot
```

每个改造点的开头都是：**"后来遇到了一个问题……"**

### 7.2 3 个必须准备的灵魂拷问

**Q1："这些功能都是你一个人完成的吗？"**

> "Agent 模块是一个团队维护的，我主要负责推理流程和工具调度这块。具体来说，ReAct 循环的 Plan 改造约 300 行、工具预筛选约 150 行、记忆管理约 250 行、动态装配约 250 行。其他同学负责前端对接和组件开发。"

**Q2："有上线吗？线上效果怎么样？"**

> "上线了。印象最深的是客服场景——上了三级压缩之后，Token 消耗降了，而且用户的订单号不会再丢了。运营团队从抱怨变成了主动推广。具体的量化数据可以在面试后提供。"

**Q3："你觉得还有哪些改进空间？"**

> "三个改进方向：
> 1. Plan 目前只有格式校验，未来可以引入多方案投票——同一个任务让 LLM 生成 3 个 Plan，选最优的
> 2. 记忆压缩的阈值目前是经验值，未来可以根据 Token 消耗自动调节
> 3. 工具预筛选目前是固定的 Top-5，未来可以根据问题复杂度动态调整——简单问题 Top-3，复杂问题 Top-8"
