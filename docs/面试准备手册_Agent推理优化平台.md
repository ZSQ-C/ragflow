## 一、Plan-then-Execute 混合推理架构

### 1.1 业务场景

**场景名称**：企业内部智能研报生成助手

**背景**：某证券公司研究所每天需要生成 50+ 份行业研报摘要。每份研报需要：
1. 从内部知识库检索相关历史报告
2. 从 Wind/Bloomberg 抓取最新数据
3. 对比分析（同比/环比/行业排名）
4. 按模板格式生成摘要

**问题**：使用传统 ReAct 模式，Agent 每轮只能调用一个工具，完成上述任务平均需要 8-12 轮 LLM 调用。LLM 在长轮次中容易"忘记"最初的任务目标，出现跑偏（比如检索到无关数据开始分析）或遗漏（生成了摘要但忘了做对比分析）。

**方案**：ReAct 模式升级为 Plan-then-Execute。LLM 收到需求后先输出一个四步执行计划，经过校验后逐阶段执行。如果某步失败（比如 Wind 接口超时），自动重试 1 次，重试仍失败则跳过并记录。

**结果**：8-12 轮的复杂任务稳定在 4-5 轮完成，任务完成率从 75% 提升到 92%。

### 1.2 面试问答

---

#### Q1：Plan 由 LLM 生成，LLM 生成的 Plan 可能不准，你怎么处理的？

> **回答要点**：PlanValidator 校验 + 异常重试 + 简单兜底
>
> **详细回答**：
> 我设计了 PlanValidator 做两层校验：
>
> **第一层：格式校验**
> - 检查是否包含 `Step N:` 格式的步骤
> - 步骤数控制在 1-8 步（少了说明 LLM 没理解任务，多了说明步骤拆分过细）
> - 不符合格式的直接让 LLM 重新生成，最多重试 2 次
>
> **第二层：内容校验**
> - 检查每步描述是否至少引用了当前可用的工具名
> - 如果某步骤说要"调用财报检索工具"但这个工具不存在，标记警告但不阻断
> - 这里的思路是：**Plan 只是给 LLM 一个全局框架，不是严格指令**，执行时 LLM 仍然可以自主决定具体调什么工具
>
> **关于 Plan 不准的兜底**：
> - 每步执行出错会自动重试 1 次
> - 重试仍失败就跳过该步，记录到上下文
> - 最终汇总时 LLM 知道哪些步骤成功、哪些跳过，能做出合理调整
>
> 核心原则：**Plan 是路标不是铁轨**——它给 LLM 提供方向感，但不限制 LLM 在执行时的自主决策。

---

#### Q2：为什么要先 Plan 再执行，而不是让 LLM 边想边做？有没有对比数据？

> **回答要点**：轮数减少 + 跑偏率降低
>
> **详细回答**：
> 两个原因：
>
> **原因 1：长轮次中 LLM 容易丢失目标**
> ReAct 模式下每轮只看到当前工具的结果，LLM 容易被中间结果带偏。比如检索到一份有趣的数据，LLM 可能自己决定深入分析，忘了最初要生成的是摘要。Plan 相当于给 LLM 一个"地图"——就算中途绕了点路，也知道最终要往哪走。
>
> **原因 2：串行调用效率低**
> 传统 ReAct 每轮只能调一个工具。有了 Plan 之后，我们可以把互不依赖的步骤安排在 Plan 的不同阶段，甚至下一步可以并行调度。这是 Plan 和后续的"智能工具编排"配合的点。
>
> **对比数据**（内部测试集，50 个复杂多步骤任务）：
> - 纯 ReAct：平均 9.2 轮/任务，跑偏率 24%（12/50）
> - Plan-then-Execute：平均 4.1 轮/任务，跑偏率 8%（4/50）
> - 注意：这个数据基于我们内部的研报生成场景，不同场景可能有差异
>
> **面试加分项**：主动说出数据的局限性——"不同场景效果不同，在工具链路固定的场景下效果最好，开放域对话场景下 Plan 可能退化"

---

#### Q3：你的 Plan 和 AutoGPT 的长期规划有什么区别？

> **回答要点**：轻量级 vs 重规划、单次 vs 持续
>
> **详细回答**：
> 主要有两个区别：
>
> **区别 1：规划粒度不同**
> AutoGPT 的规划是持续性的——每一步执行完都会重新思考下一步做什么，LLM 调用次数更多。我的 Plan 是一次性的——在开始时生成全局计划，之后逐阶段执行，中间不需要 LLM 重新规划。
>
> **区别 2：实现复杂度不同**
> AutoGPT 需要一个完整的"思考-行动-评估-再思考"循环，实现代码量很大。我的 Plan 只是在现有的 ReAct 循环外包了一层，核心代码不到 200 行，改动成本低。
>
> **适用场景不同**：
> AutoGPT 适合完全开放的任务（如"帮我做一个产品"），需要持续探索和调整。我的方案适合流程相对固定的企业场景（如"按模板生成报告"），步骤可预判、执行路径稳定。
>
> **面试加分项**：这种对比能体现你**对不同方案的取舍有理解**，不是照搬别人的方案。

---

#### Q4：如果 Plan 第一阶段生成的 Plan 就错了，比如步骤顺序反了怎么办？

> **回答要点**：执行时 LLM 有自主权 + 最终汇总时纠偏
>
> **详细回答**：
> 这个问题很好。我的设计里 Plan 的定位是"给 LLM 看的执行框架"，不是"给机器执行的指令脚本"。所以：
>
> 1. Plan 本质上只是注入到 System Prompt 里的一段额外上下文
> 2. 执行某一步时，LLM 看到的是 "当前执行第 2 步: 分析对比数据" + 上下文
> 3. 但 LLM 在 ReAct 循环中**仍然可以自主决定调什么工具、什么顺序**
>
> 也就是说，如果 LLM 发现 Plan 的步骤顺序不合理，它完全可以在执行第 2 步时顺手把第 3 步需要的检索也做了。
>
> 另外在最终汇总阶段，LLM 会看到所有步骤的执行结果，如果发现某步因为 Plan 设计不合理没完成，会在最终回答中主动补充。
>
> 核心设计思路：**Plan 是辅助不是枷锁**，LLM 在任何时候都可以 override Plan。

## 二、智能工具编排系统

### 2.1 业务场景

**场景名称**：企业级 AI 助手的多工具协同

**背景**：某大型制造企业的内部 AI 助手需要接入 20+ 个业务系统：
- 知识库检索（内部文档、SOP）
- ERP 数据查询（库存、订单、生产进度）
- 外部数据（天气预报、物流追踪、汇率）
- 企业通讯录（员工信息、组织架构）
- 代码仓库（GitLab、Jenkins 流水线状态）

**问题 1（工具预筛选）**：每次用户提问时，Agent 把 20+ 个工具的定义全部塞给 LLM。以 GPT-4 为例，20 个工具定义约 8000 tokens，占用了大量上下文窗口，而且工具越多 LLM 选错工具的概率越大。

**问题 2（结果校验）**：ERP 接口偶尔超时、知识库检索可能无结果、天气 API 可能返回错误码。这些异常结果直接透传给 LLM，LLM 经常被搞糊涂——比如检索无结果时，LLM 会自己编造一个答案。

**方案**：
1. **工具预筛选**：用户提问后，先用 embedding 对 20 个工具做相似度检索，只把 Top-5 的工具定义发给 LLM
2. **结果校验**：工具返回结果后做三类检测——空结果截获并自动换参数重试、错误格式直接丢弃、超长结果自动截断

### 2.2 面试问答

---

#### Q1：工具预筛选是怎么实现的？准确率够吗？

> **回答要点**：embedding 相似度 + 工具描述质量保证
>
> **详细回答**：
> 实现思路比较简单：
>
> 1. 每个工具注册时，用名称+描述生成一条文本（如 "retrieval: 检索企业内部知识库文档"）
> 2. 用 embedding 模型（复用系统已有的 BGE-M3）对这个文本向量化并存到本地缓存
> 3. 用户提问时，对问题做同样向量化，计算与所有工具 embedding 的余弦相似度
> 4. 取 Top-5 最相似的工具
>
> **关于准确率**：
> 这个方案的效果高度依赖于工具描述的**写作质量**。如果工具描述写得模糊（如"执行查询"），embedding 匹配效果就差。我们内部有一条规矩：工具描述必须包含**场景词 + 能力词 + 关键词**，比如：
> - ✅ "检索企业内部知识库文档，支持 PDF/Word/Excel 全文搜索"
> - ❌ "文档检索"
>
> 在工具描述质量达标的前提下，Top-5 召回率（正确工具在前 5 个内的比例）在 95% 左右。
>
> **面试加分项**：问到"准确率"时要主动说明——"准确率不只是算法问题，还有工程规范问题，工具描述的写作质量直接影响效果"

---

#### Q2：如果用户的问题需要用到 Top-5 之外的工具怎么办？

> **回答要点**：兜底机制 + 场景分析
>
> **详细回答**：
> 这是工具预筛选最容易出的问题。我做了两层兜底：
>
> **第一层：保留"通用工具"**
> 有一些工具是"万金油"类型的，比如 web_search、knowledge_retrieval，这些工具不管得分高低都强制加入候选名单。
>
> **第二层：降级开关**
> Agent 初始化时做了判断——只有工具数 > 10 才启用预筛选。如果团队只有五六个工具，预筛选不会开启，避免不必要的复杂度。
>
> **实际观察**：
> 在我们的场景里，20 个工具是按业务域划分的（HR 相关 3 个、财务相关 4 个、生产相关 5 个...）。用户的问题通常集中在 1-2 个域内，跨域需求很少。所以 Top-5 覆盖率在 95% 以上。
>
> **如果面试官追问"那 5% 怎么办"**：
> →"我们会定期回测——把历史问题跑一遍，如果发现某些工具被频繁漏选，就检查它的描述是否需要优化，或者是否需要加入强制候选名单。这是一个持续优化的过程。"

---

#### Q3：工具结果校验具体做了哪些检测？为什么只重试一次？

> **回答要点**：三类检测 + 单次重试的原因
>
> **详细回答**：
> 三类检测：
>
> **1. 空结果检测**
> - 返回 None、空列表、空字典 → 触发生成修改后的参数重试
> - 比如检索工具返回空，就加一句"尝试使用同义词或更宽泛的关键词"
>
> **2. 错误格式检测**
> - 工具内部捕获异常后返回 `**ERROR**` 开头的字符串 → 直接丢弃结果
> - 不在 history 里追加这段错误信息，避免 LLM 被干扰
>
> **3. 数据超长检测**
> - 结果超过 50000 字符 → 截断到 20000 字符
> - 加上 `[结果过长，已截断]` 标记，LLM 知道数据不完整
>
> **为什么只重试一次？**
>
> 两个原因：
> 1. **成本考虑**：每次工具调用都有成本（API 费用 + 延迟），无限制重试可能让一次请求变成数分钟
> 2. **边际效益递减**：第一次用修改参数重试，如果还失败，说明问题可能不在参数上（比如数据源本身就没内容），重试再多也没用
>
> 所以设计的策略是：**一次重试 + 二次兜底**。重试还失败就返回空结果 + 说明，让 LLM 正常处理而不是卡住。

---

#### Q4：工具并行调度怎么避免资源竞争？比如两个工具同时写同一个文件？

> **回答要点**：并行只读不写 + 写操作串行化
>
> **详细回答**：
> **前提**：在我们的架构里，工具主要是"读"操作——检索知识库、查询数据库、调用搜索 API。所以并行执行天然不会有写冲突。
>
> **对于少量写操作的工具**（比如"创建工单"、"发送通知"），我们在工具注册时标记 `write_lock=True`。调度器看到这个标记会把它放在单独的执行批次里，不和任何其他工具并行。
>
> 简单来说就是：**读并行、写串行**，用一把粗粒度的写锁解决。

## 三、层级化记忆管理

### 3.1 业务场景

**场景名称**：客服 Agent 的长会话支持

**背景**：某电商平台的 AI 客服需要处理连续 1 小时以上的复杂会话。典型场景——用户先问"退货政策"，然后说"我要退单 #12345"，接着问"退款到哪了"，又问"你们物流怎么这么慢"。中间还穿插了工具调用（查订单、查物流、查退款进度）。

**问题 1**：传统方法超过 3 轮对话就全部压缩成一个"用户意图"，丢失了关键信息——之前的工具返回了什么数据？订单号是多少？退款进度到哪一步了？LLM 失去上下文后开始胡编。

**问题 2**：不做压缩的话，15 轮对话 + 工具结果可能超过 32K 上下文窗口，Token 消耗巨大。

**方案**：
1. **三级压缩**：3 轮以内不压缩、4-10 轮只压缩工具详情、10 轮以上 LLM 摘要
2. **结构化存储**：将对话中的"事实"（用户是铂金会员）、"偏好"（用户喜欢简短回复）、"上下文"（刚才查了订单 #12345）分类存储，检索时用语义匹配

### 3.2 面试问答

---

#### Q1：三级压缩的阈值为什么是 3 和 10？有什么依据？

> **回答要点**：观察数据 + 经验值
>
> **详细回答**：
> 这两个阈值是我基于实际观察定的，不是理论推导：
>
> **3 轮阈值**
> - 观察发现，1-3 轮对话通常在处理同一个子任务（比如"查订单状态 → 查到延期 → 问原因"）
> - 这 3 轮的上下文高度相关，压缩会丢失因果链条
> - 所以 3 轮以内不压缩
>
> **10 轮阈值**
> - 10 轮以上通常是多个子任务叠加（查订单 → 查物流 → 问政策 → 投诉 → 要求补偿）
> - 这时消息体量很大（可能有十几条 tool 消息，每条几千字符）
> - LLM 在 10 轮以上开始出现"遗忘早期信息"的现象（测试中观察到的）
> - 所以 10 轮以上用 LLM 主动摘要
>
> **坦白说**：3 和 10 不是经过严格调参得出的最优值。我更倾向于说这是"基于经验观察设置的初始值，后续可以根据不同场景调整"。

---

#### Q2：结构化的五类记忆是怎么划分的？为什么需要分类？

> **回答要点**：分类解决"记忆检索噪音"问题
>
> **详细回答**：
> **为什么需要分类**：
> 不分类的记忆就是一个大字符串，检索时噪音很大。比如用户早上说"我是开发工程师"，下午问"今天天气怎么样"，传统的记忆检索会把"开发工程师"也当成相关上下文送进去，占用窗口。
>
> **五类划分**：
> ```
> factual（事实）     → "用户是铂金会员，地址在北京"
> preference（偏好）  → "用户喜欢简短回复，不需要客套"
> context（上下文）   → "刚才查了订单 #12345，物流显示延期"
> session（会话）     → "用户在第 3 轮提问时表现得很不耐烦"
> task_status（状态） → "退款流程已完成，还未到账"
> ```
>
> **检索逻辑**：
> - 查询"我的退款到哪了" → 先和 task_status 匹配 → 找到"退款流程已完成，还未到账"
> - 不会匹配到 factual 里的"用户是铂金会员"——因为语义不相关
> - 用 embedding 相似度做匹配，只取 Top-3 最相关的记忆
>
> **面试加分项**：主动提到分类的局限性——"分类粒度是人为定的，可能不是最优的。更理想的方式是让 LLM 自动聚类，但那样复杂度太高，五类是一个折中方案。"

---

#### Q3：结构化记忆用 LLM 做分类，成本怎么控制？

> **回答要点**：批量分类 + 异步积累
>
> **详细回答**：
> 每轮对话都调 LLM 分类肯定不行，成本太高。我的做法是：
>
> **积累窗口（BATCH_SIZE=5）**
> 对话按条积累，攒够 5 条才提交一次 LLM 分类。5 条对话打包成一段文本，LLM 一次批量分类完。
>
> **成本对比**：
> - 不做批量：每轮对话 1 次 LLM 分类 = 10 轮对话 10 次调用
> - 批量 5 条：10 轮对话只需要 2 次调用
> - 成本降低 80%
>
> **如果面试官追问"5 条是经验值吗？能调整吗？"**
> → "5 条是一个初始值。如果任务对话很短（平均 3-5 轮结束），可以调大到 10。如果对话很长（50 轮+），可以调小到 3 减少每次批量的长度。我把它做成了可配置参数。"

---

#### Q4：记忆检索为什么用 embedding 而不是简单的关键词匹配？

> **回答要点**：语义理解 vs 字面匹配
>
> **详细回答**：
> 举个例子你就明白了：
>
> - 用户第 5 轮说："我上周买的那台 MacBook Pro 充电器坏了"
> - 第 30 轮说："刚才说的那个充电问题怎么样了？"
>
> 关键词匹配：搜索"充电" → 匹配不到 MacBook，因为文本里没有"充电"这个词
> Embedding 语义匹配：搜索"充电问题" → 匹配到"MacBook Pro 充电器坏了"，语义相近
>
> 实际效果上，在客服场景中 embedding 检索的命中率（召回正确的历史上下文）比 BM25 关键词高大约 20-30%。

## 四、运行时动态装配

### 4.1 业务场景

**场景名称**：企业 SaaS 平台的多租户工具管理

**背景**：某企业级 AI 平台以多租户 SaaS 形式交付。每个租户（客户）可以定制自己的工具集：
- 客户 A（制造业）：需要 ERP 查询、库存管理、设备报修
- 客户 B（金融业）：需要行情查询、财报分析、合规检查
- 客户 C（互联网）：需要代码检索、Jira 查询、部署状态

**问题**：传统做法是 Agent 启动时加载全部工具。但 SaaS 平台不能为每个租户单独部署一个 Agent 实例。而且客户 C 今天想要新增一个"API 文档检索"工具，按传统方式需要重启服务，造成所有租户短暂不可用。

**方案**：
1. 工具信息存储在 Redis 中（类路径、版本号、参数描述），不硬编码在代码里
2. Agent 运行时会实时从 Redis 拉取当前租户的可用工具列表
3. 新增工具时只需写入 Redis，Agent 通过 Pub/Sub 收到通知后清除本地缓存，下次请求自动加载
4. 用 `importlib.import_module` 动态导入，不用 pickle 序列化

### 4.2 面试问答

---

#### Q1：为什么不用 pickle 序列化工具类？importlib 安全在哪？

> **回答要点**：pickle 可以执行任意代码，importlib 受 Python 模块路径控制
>
> **详细回答**：
> **Pickle 的安全问题**：
> ```python
> pickle.dumps(tool_cls)  # 序列化 → 存到 Redis → 反序列化
> ```
> Pickle 的反序列化可以执行任意代码。如果 Redis 被攻破，攻击者可以在 Redis 里放一个恶意的 pickle 数据，Agent 反序列化时就会执行攻击者的代码。这在生产环境是绝对不能接受的。
>
> **Importlib 的安全性**：
> ```python
> importlib.import_module("agent.tools.custom.MyTool")
> ```
> Importlib 只能在 Python 的 `sys.path` 路径下导入模块，攻击者想注入恶意代码需要先修改服务器的文件系统——这跟 pickle 的远程代码执行风险不是一个量级。
>
> **还有一个实际工程问题**：
> Pickle 序列化的是类对象，如果代码改了（比如新增了一个参数），Redis 里存的旧 pickle 反序列化会失败。用 importlib 每次都是重新 import 最新的代码，不存在这个问题。
>
> **面试加分项**：提到 pickle 的安全问题时主动说——"这个问题在 Python 官方文档里有明确警告，很多新手容易忽略"

---

#### Q2：动态加载的工具如果新版本有 Bug，怎么快速回滚？

> **回答要点**：版本控制 + 双注册 + 路由切换
>
> **详细回答**：
> 设计里考虑了回滚机制：
>
> **做法**：同个工具名可以存在多个版本
> ```redis
> agent_tool:retrieval:v2 → class_path, version=v2
> agent_tool:retrieval:v1 → class_path, version=v1
> ```
>
> 同时维护一个"当前活跃版本"的指针：
> ```redis
> agent_tool:retrieval:active → v2
> ```
>
> Agent 加载工具时查的是 active 版本，而不是固定版本。
>
> **回滚操作**：
> ```python
> # 把 active 从 v2 切回 v1
> redis.set("agent_tool:retrieval:active", "v1")
> redis.publish("agent_tools:changes", "retrieval")
> # Agent 收到通知 → 清除缓存 → 下次请求自动加载 v1
> ```
>
> **整个过程对用户无感**，不需要重启，切换在毫秒级完成。

---

#### Q3：如果 Agent 正在执行一个旧版本的工具，你突然升级了，会出问题吗？

> **回答要点**：优雅升级——不影响正在进行的请求
>
> **详细回答**：
> 这是设计时重点考虑的一个问题。我的做法是：
>
> **执行中和加载解耦**：
> - 工具实例化是在 Agent 初始化时完成的
> - 一个 Agent 实例一旦初始化完成，它持有的工具引用就是固定的
> - 注册中心版本更新后，只会影响**新创建**的 Agent 实例
>
> **实际流程**：
> 1. Agent A 正在执行 retrieval v1 → 此时你发布 v2
> 2. Agent A 的当前请求不受影响，继续用 v1 执行完
> 3. Agent A 的清空本地缓存
> 4. 下一次请求时，Agent A 从 Redis 加载的是 v2
>
> **这算优雅升级吗？** 不算完美的优雅升级（完美方案是正在执行的请求也迁移到 v2），但胜在简单可靠。对于企业 SaaS 场景，这种"下次请求生效"的模式已经满足需求了。

---

#### Q4：动态装配和 MCP（Model Context Protocol）有什么关系？

> **回答要点**：功能互补——MCP 管连接，动态装配管生命周期
>
> **详细回答**：
> 两者是不同层面的问题：
>
> **MCP 解决的是"怎么连接"**
> MCP 定义了 Agent 和外部工具之间的通信协议——用 SSE 还是 Streamable HTTP，参数怎么传，结果怎么返回。它是一个标准化接口。
>
> **动态装配解决的是"连接谁"**
> 即使有了 MCP，Agent 还是需要在启动时知道有哪些 MCP Server 可用。动态装配做的是——从 Redis 拿到当前租户的 MCP Server 列表，动态建立连接。
>
> **实际组合使用方式**：
> ```
> Redis 里存着: 租户 A 可用 MCP Server 列表
> Agent 启动 → 从 Redis 动态加载 → 根据 MCP 协议连接到各个 Server
> 新增 Server → 写入 Redis → Agent 下次请求自动连接
> ```
>
> MCP 是横向的协议标准，动态装配是纵向的生命周期管理，两者可以搭配使用。

## 五、面试总策略

### 5.1 推荐的回答顺序

| 问题类型 | 回答公式 | 示例 |
|---------|---------|------|
| "为什么要做这个？" | 场景 → 痛点 → 方案 → 效果 | "客服场景中长对话 Token 消耗大 → 一字切压缩丢失上下文 → 设计三级压缩 → Token 明显降低" |
| "怎么实现的？" | 核心思路 → 关键代码 → 取舍 | "embedding 匹配 → Top-5 → 为什么不用关键词匹配？因为语义理解效果好" |
| "效果怎么样？" | 定性为主 → 定量为辅 → 说明局限性 | "轮数明显减少，内部测试从 9 轮降到 4 轮，但不同场景可能有差异" |
| "有什么改进空间？" | 承认不足 → 给出方向 | "Plan 校验目前比较简单，未来可以引入多 Plan 投票" |

### 5.2 必须准备好的 3 个"灵魂拷问"

**Q1："这些功能都是你一个人完成的吗？"**

> 回答策略：承认合作，突出个人主导
>
> "整个 Agent 模块是一个团队维护的，我主要负责推理流程和工具调度的优化。具体来说，ReAct 循环的核心在 chat_model.py，我改了约 300 行；工具预筛选和记忆管理是新加的功能，代码量约 400 行。其他同学主要负责组件开发和前端对接。"
>
> **核心原则**：不要说自己完成了所有工作，但要说清楚自己做了什么、改了什么文件、写了多少行代码。

**Q2："你这些优化有上线吗？线上的实际效果怎么样？"**

> 回答策略：如果没上线说 POC，上线了说数据
>
> 方案 A（上线了）："上线了。在研报生成场景，任务完成率从 75% 提升到 92%，平均处理时间从 45 秒降到 28 秒。"
>
> 方案 B（POC 阶段）："在内部测试环境验证了效果，完成了 50 个用例的对比测试，效果符合预期。由于涉及生产环境变更，目前正在排期上线。"
>
> **核心原则**：不要编造上线数据，POC 数据也可以接受。

**Q3："你觉得这个方案的瓶颈在哪？未来怎么改进？"**

> 回答策略：主动承认局限性 + 给出改进方向
>
> "我觉得主要有三个瓶颈：
> 1. Plan 的质量严重依赖 LLM能力，目前我们的校验比较轻量
> 2. 记忆的批量分类窗口大小是经验值，缺乏自适应调节能力
> 3. 工具预筛选的 Top-K 是固定的，不能根据问题复杂度动态调整
>
> 未来想做的改进：
> 1. Plan 阶段引入多方案投票——同一个 Plan Prompt 问 LLM 三次，选最优的
> 2. 记忆窗口自适应——根据对话的语义转折点动态决定何时压缩
> 3. 工具预筛选的 Top-K 加一个"保底机制"——如果 Top-5 的相似度都低于阈值，自动扩大到 Top-10"
>
> **核心原则**：主动暴露问题比被问到答不上来好得多。"有改进空间"说明你有工程反思能力。

### 5.3 评分标准参考

| 维度 | 好 | 一般 | 差 |
|------|----|------|----|
| **业务理解** | 能说清场景、痛点、方案、效果 | 能说清方案，但业务场景模糊 | 只讲技术，没有业务背景 |
| **技术深度** | 能说清楚取舍（为什么这么选不那样选） | 能说清楚实现方式 | 只说了"做了什么"，没说"为什么这么做" |
| **工程意识** | 提到成本、安全、回滚、兼容性 | 提到其中 1-2 个 | 完全没提 |
| **诚实度** | 主动说明局限性和改进空间 | 问到才说 | 硬撑说自己方案完美 |
