## 一、Plan-then-Execute 混合推理架构

### 1.1 场景故事（一句话）

> **运营同事说："帮我写一份上周的线上事故报告，包含事故数量、影响范围、处理进度。"**
>
> 然后 Agent 开始干活——先查 Jira、再查 GitLab、再查值班表……干了 10 轮，最后输出了一份报告，但报告里只分析了某一个 Bug，完全忘了最初要的是"整体报告"。

### 1.2 大白话讲问题

原来的 Agent 工作方式是**走一步看一步**。就像你让一个实习生去写报告，他不先想好要查什么、从哪查，而是查到一个数据就开始分析，分析到一半发现还得查另一个数据，查完回来已经忘了最初要干嘛了。

LLM 也是这样。每轮只看到当前工具返回的结果，很容易被中间信息带偏。

而且随着公司越来越多部门接入，问题变得更复杂了：

```
财务部问："帮我分析 Q2 华东区营收"
  → Agent 跑去查了 GitLab 代码仓库……财务连 GitLab 是什么都不知道

运营部问："写一份事故复盘报告"
  → Agent 第一轮去查了知识库，第二轮去查了 Jira
  → 第三轮突然去查了天气 API（？）
  → 它调了一个不在授权范围内的工具，没人发现
```

这就暴露了两个问题：
1. **不同部门看到的工具集应该不一样**——财务不该看到 GitLab，研发不该看到 ERP
2. **计划里提到的工具必须是真实存在的**——不能让 LLM 自己编一个工具名

### 1.3 大白话讲思路

我的做法是给原来的"先计划再执行"加了一层"前置处理"和一层"后置审查"，变成了一个完整的 6 步流程：

```
用户提问
  │
  ▼
① 场景分类 → 确定用哪组工具（财务/研发/运营）
  │
  ▼
② 生成执行计划（带上可用工具清单，输出 JSON）
  │
  ▼
③ 校验计划（格式、工具存在性、逻辑依赖）
  │
  ▼
④ 逐步执行（带缓存 + 结果快速检查 + 高风险操作暂停确认）
  │
  ▼
⑤ 汇总草稿 + 可信度审查
  │
  ▼
⑥ 输出最终答案（或低分时追问用户）
```

每一步都不动原有的 ReAct 循环，只是在外面加包装层。

### 1.4 代码实现流程（大白话版）

#### 第一步：用户提问 → 先判断场景，缩小工具范围

```python
# 用户说："帮我分析 Q2 华东区营收对比"
#
# 原来的做法：所有 20 个工具都摆出来让 LLM 选
# 我的做法：先判断这是哪个业务线的问题，只给对应的工具

# ① 轻量级场景分类
# 用一个简单的 Prompt 让 LLM 判断场景
scene_prompt = """
根据用户问题判断所属场景，只输出一个词：
财报分析 / 事故复盘 / 客户投诉 / 合同审查 / 通用问答
"""
scene = await llm.chat(scene_prompt, user_query)
# 返回："财报分析"

# ② 根据场景路由到对应的工具子集
tool_router = {
    "财报分析": ["财报检索", "SQL查询", "趋势绘图"],
    "事故复盘": ["知识库检索", "Jira查询", "GitLab查询", "报告模板库"],
    "客户投诉": ["CRM查询", "工单系统", "邮件发送"],
    "合同审查": ["文档解析", "条款比对", "法规库"],
    "通用问答": ["通用搜索", "知识库检索"]
}
available_tools = tool_router.get(scene, ["通用搜索"])

# 企业价值：
# - 财务看不到 GitLab，研发看不到 ERP，安全
# - LLM 收到的工具描述少了，选错概率降低
# - Prompt 里的 Token 消耗减少
```

#### 第二步：带着工具清单生成计划（JSON 格式）

```python
# 原来的计划 Prompt 是自由文本格式
# 改成严格 JSON 格式，每步必须绑定一个工具

plan_prompt = f"""
你是一个企业智能助手，当前可用的工具只有：{available_tools}
请根据用户问题，生成一个多步骤执行计划，
每一步都必须明确使用哪个工具。

输出 JSON 数组格式（不要输出其他内容）：
[
  {{"step": 1, "tool": "工具名", "action": "执行描述"}},
  {{"step": 2, "tool": "工具名", "action": "执行描述"}}
]

最多不超过 8 步。
如果无法规划，输出 [] 。
"""

plan = await llm.chat(plan_prompt, user_query)
# LLM 返回（JSON 格式）：
# [
#   {"step": 1, "tool": "财报检索", "action": "获取2024Q2营收明细"},
#   {"step": 2, "tool": "SQL查询", "action": "计算华东区环比增长率"},
#   {"step": 3, "tool": "趋势绘图", "action": "生成营收趋势图"}
# ]

# JSON 格式的好处：可以直接用代码解析，不需要正则匹配
import json
plan_steps = json.loads(plan)  # 一步到位
```

#### 第三步：三层计划校验

```python
class PlanValidator:
    def __init__(self, available_tools):
        self.tool_set = set(available_tools)
        # 工具依赖规则：从工具元数据中读取，不硬编码
        # 比如"趋势绘图"注册时声明了 depends_on=["SQL查询"]
        # 这样不同部门的依赖规则可以不同，不用改代码
        self.dependency_rules = self._load_dependency_rules(available_tools)
    
    def validate(self, plan_steps):
        # 第一层：基础格式检查
        if not isinstance(plan_steps, list) or len(plan_steps) == 0:
            return False, "计划为空或格式错误"
        if len(plan_steps) > 8:
            return False, "步骤数超过上限 8"
        
        # 第二层：工具存在性检查（硬拦截）
        for step in plan_steps:
            tool_name = step.get("tool", "")
            if tool_name not in self.tool_set:
                # 这是硬拦截——LLM 想调用一个不存在的工具
                # 直接拒绝，要求重新生成
                return False, f"步骤 {step['step']} 使用了未授权的工具 '{tool_name}'"
        
        # 第三层：工具依赖逻辑检查
        # 比如"趋势绘图"依赖"SQL查询"先执行
        # 这个依赖关系是工具注册时自己声明的，不是写死的
        for step in plan_steps:
            tool_name = step["tool"]
            if tool_name in self.dependency_rules:
                required_tools = self.dependency_rules[tool_name]
                preceding = [s["tool"] for s in plan_steps if s["step"] < step["step"]]
                for req in required_tools:
                    if req not in preceding:
                        return False, f"步骤 {step['step']} ({tool_name}) 依赖 {req} 先执行"
        
        return True, "校验通过"

# 企业价值：  
# - 工具存在性检查是"硬拦截"——不存在的工具直接报错
# - 依赖规则从工具自身的元数据读取，不是硬编码字典
#   新增工具时只需要在工具注册时声明依赖关系
```

#### 第四步：逐步执行（缓存 + 结果验证 + 高风险确认）

这是整个流程的核心。每执行一步做三件事。

```python
# ① 请求级缓存：相同工具+相同参数不重复调用
cache = {}  # 这个缓存只在当前请求生命周期内有效

async def execute_with_cache(tool_name, action_params):
    # 用工具名+参数做一个稳定的缓存 key
    # action_params 是结构化参数（dict），不是字符串
    # 所以要先序列化再 hash
    import hashlib
    raw_key = f"{tool_name}:{json.dumps(action_params, sort_keys=True)}"
    cache_key = hashlib.md5(raw_key.encode()).hexdigest()
    
    if cache_key in cache:
        print(f"命中缓存，跳过执行: {tool_name}")
        return cache[cache_key]
    
    result = await call_tool(tool_name, action_params)
    cache[cache_key] = result
    return result


# ② 步骤结果快速验证
# 不同工具类型有不同的"成功"标准，在工具注册时声明
# 比如：检索类工具要求 chunks 不为空
#       SQL查询要求返回列表不为空
def check_step_result(tool_name, result):
    rules = {
        "财报检索": lambda r: len(r.get("chunks", [])) > 0,
        "SQL查询": lambda r: isinstance(r, list) and len(r) > 0,
        "知识库检索": lambda r: len(r.get("chunks", [])) > 0,
    }
    checker = rules.get(tool_name)
    if checker and not checker(result):
        return False, f"{tool_name} 返回空结果，请调整查询条件重试"
    return True, ""


# ③ 高风险操作的人工确认
# 有些操作不能自动执行，需要用户点头
HIGH_RISK_TOOLS = ["邮件发送", "工单创建", "数据库写入"]

async def execute_plan(plan_steps, on_confirm=None):
    completed = []
    for step in plan_steps:
        tool_name = step["tool"]
        action = step["action"]
        
        # 风险操作确认
        if tool_name in HIGH_RISK_TOOLS and on_confirm:
            # 发出确认请求，等待用户回复
            confirmed = await on_confirm(f"即将执行 {tool_name}: {action}，是否继续？")
            if not confirmed:
                completed.append(f"步骤 {step['step']} ({tool_name}) 已被用户取消")
                continue
        
        # 执行（带缓存）
        result = await execute_with_cache(tool_name, {"query": action})
        
        # 结果验证
        valid, msg = check_step_result(tool_name, result)
        if not valid:
            # 一次自我纠错机会：把错误信息给 LLM，让它改参数重试
            corrected = await llm.chat(
                f"上一步执行失败：{msg}，请给出修正后的查询参数",
                {"tool": tool_name, "original": action}
            )
            result = await execute_with_cache(tool_name, corrected)
        
        completed.append(result)
    
    return completed
```

#### 第五步：汇总 + 可信度审查（一次 LLM 调用完成）

```python
# 所有步骤执行完后，生成最终回答并做可信度检查
# 原来：先生成 → 再审查 → 再追问（3 次 LLM 调用）
# 优化后：一次 LLM 调用同时生成回答和可信度评分

final_prompt = f"""
你是一个企业智能助手。以下是根据用户问题执行各步骤后得到的结果。

用户问题：{user_query}
各步骤产出：{completed_contexts}

请完成两项工作：
1. 根据以上信息生成最终回答
2. 对回答的可信度进行评分（0-1），考虑以下因素：
   - 步骤执行是否全部成功
   - 数据是否完整
   - 推理逻辑是否自洽

输出 JSON 格式：
{{
  "answer": "最终回答内容",
  "confidence": 0.85,
  "issues": ["步骤2返回的数据不完整，结论可能不准确"]
}}
"""

result = await llm.chat(final_prompt)

if result["confidence"] < 0.5:
    # 低可信度 → 不直接回答，转为追问
    clarifying = f"根据当前获取到的信息，我还无法给出可靠回答。{result['issues'][0] if result['issues'] else ''}，请补充更多信息。"
    yield {"type": "clarify", "question": clarifying}
else:
    # 高可信度 → 输出带置信度的回答
    confidence_badge = f"\n\n（本回答可信度：{result['confidence']*100:.0f}%）"
    yield result["answer"] + confidence_badge
```

### 1.5 完整流程总结

加上上述增强后，Plan-then-Execute 变成了一个完整的 6 阶段流程：

```
用户提问
  │
  ▼
① 场景分类 + 工具路由
   ├── 轻量 LLM 判断场景（财报/事故/投诉/合同/通用）
   └── 根据场景选择工具子集（安全隔离 + Token 节省）
  │
  ▼
② 工具感知的计划生成（JSON 格式）
   ├── Prompt 中明确列出可用工具
   └── 每步必须绑定一个具体工具
  │
  ▼
③ 三层计划校验
   ├── 格式检查（JSON 解析、步骤数量）
   ├── 工具存在性硬拦截（不存在的工具直接拒绝）
   └── 依赖逻辑检查（从工具元数据读取，非硬编码）
  │
  ▼
④ 逐步执行循环
   ├── 请求级缓存（相同工具+参数不重复调用）
   ├── 结果快速验证（根据工具类型检查结果是否有效）
   ├── 一次自我纠错（无效结果让 LLM 改参数重试）
   └── 高风险操作人工确认（发邮件/创建单需要用户点头）
  │
  ▼
⑤ 汇总草稿 + 置信度评估（一次 LLM 调用）
   ├── 同时生成回答和可信度评分
   └── 低分（<0.5）自动转为追问，不输出不可靠回答
  │
  ▼
⑥ 输出最终答案（带可信度标记）
```

和原来相比，核心变化是：

| 维度 | 原来的 Plan-then-Execute | 增强后 |
|------|------------------------|--------|
| 工具范围 | 全部工具 | 按场景路由的子集 |
| 计划格式 | 自由文本 | JSON（可直接解析） |
| 工具校验 | 警告但不阻断 | 硬拦截 + 依赖检查 |
| 执行效率 | 每步都调 LLM | 缓存去重 |
| 结果可靠性 | 透传工具结果 | 验证 + 自我纠错 |
| 安全性 | 无 | 高风险操作确认 |
| 输出可信度 | 无 | 置信度评分 + 低分追问 |

### 1.6 面试官可能会追问

**问："场景分类又多了一次 LLM 调用，成本怎么控制？"**

> 这个分类用的是一次极简的 LLM 调用——Prompt 只有几十个 Token，模型用最快的（比如 GPT-4o-mini），单次成本可以忽略不计。而且它带来的好处远大于成本：一方面过滤掉了无关工具，后续每次 LLM 调用的 Token 都减少了；另一方面防止了跨部门工具越权，这是安全收益，不能用成本衡量。

**问："JSON 格式的计划如果 LLM 输出格式不对怎么办？"**

> 分两种情况：如果是少量格式错误（比如多了一个逗号），我用 `json_repair` 库自动修复。如果是完全乱来（比如输出了散文而不是 JSON），PlanValidator 会检测到格式错误，要求 LLM 重新生成，最多重试 2 次。实测中 GPT-4 级别的模型按这个 Prompt 输出 JSON 的成功率在 99% 以上。

**问："工具依赖规则写死在代码里，新工具接入不是很麻烦？"**

> 依赖规则不是硬编码的。每个工具注册时可以在元数据里声明 `depends_on` 字段，PlanValidator 启动时从工具注册中心读取。这样新增工具时只需要在注册信息里写清楚依赖关系，不需要改 PlanValidator 的代码。

**问："置信度评分让 LLM 自己给自己打分，会不会不客观？"**

> 这个问题问得好。我主要用它来捕捉**明显的失败场景**——比如某步骤返回了空结果、某个工具报错了。这些情况下 LLM 自己也知道数据不可靠，confidence 会打得很低。对于"数据看起来都对但其实是错的"这种情况（比如 LLM 幻觉），置信度评分确实不一定能发现。所以我的策略是：**低分直接拦截（精确率高），高分不保证绝对正确，但至少让使用者知道风险。** 加了置信度标记之后，运营团队反馈说"看到 90% 以上的回答我们就直接用了，低于 60% 的我们会复查一下"。

## 二、智能工具编排系统

### 2.1 场景故事（一句话）

> **运营同事说："我让它查一个 Jira 工单，它去查了知识库，浪费了好几分钟。"**
>
> 同时：
> **运营同事又说："它说查到了事故记录，但点开链接是空的。"**

### 2.2 大白话讲问题

项目接入了 20 多个业务系统：Jira、GitLab、知识库、值班表、Jenkins……每次用户提问时，我们把 20 个工具的说明书全部发给 LLM，让 LLM 自己选用哪个。这就好比：

> 你让一个实习生去帮你拿一份文件，但你先把公司所有的规章制度、操作手册、通讯录全部拍在他桌上，说"你自己找"。

实习生面对 20 本手册，很容易拿错。

同时，工具本身也不靠谱。有时候工具说"查到了"，但返回的是个空结果。LLM 拿到空结果也不知道该怎么办，有时会自己编一个答案。

### 2.3 大白话讲思路

两个问题，两个解法：

**问题 1：工具太多，LLM 选不对**
解法：先自己筛一遍，只给 LLM 最有可能用到的 5 个工具。

**问题 2：工具结果不可靠**
解法：工具返回的结果先检查一遍，有问题就自动重试，重试还失败就告诉 LLM"这个工具不可用"。

### 2.4 代码实现流程（工具预筛选）

#### 第一步：给每个工具生成一个"身份证"

```python
# 每个工具有一个名字和一段描述
# jira_tool: "查询 Jira 工单状态、Assignee、Sprint 信息"
# knowledge_tool: "检索企业内部知识库文档，支持 PDF/Word/Excel"
# gitlab_tool: "搜索 GitLab 代码仓库，查找代码变更记录"

# 我用 embedding 模型把"名字+描述"转成一个向量（也就是一堆数字）
tool_embedding = embedding_model.encode("jira_tool: 查询 Jira 工单状态...")
# 这堆数字就代表了这个工具的"语义"
```

#### 第二步：用户提问时，把问题也转成向量

```python
# 用户说："帮我查一下 Jira 上那个线上事故的工单"
query_embedding = embedding_model.encode("帮我查一下 Jira 上那个线上事故的工单")
```

#### 第三步：计算问题向量和每个工具向量的相似度

```python
scores = []
for name, embedding in tool_embeddings.items():
    score = cosine_similarity(query_embedding, embedding)
    scores.append((name, score))
    
# 排序，取前 5 个
scores.sort(reverse=True)
selected_tools = scores[:5]

# 结果可能是：
# 1. jira_tool (0.92)  → 最相关
# 2. knowledge_tool (0.45)
# 3. gitlab_tool (0.30)
# 4. ...
# 5. ...

# 只把这 5 个工具的定义发给 LLM
# 其他 15 个工具的定义不发了，省 Token
```

#### 第四步：一些兜底逻辑

```python
# 有些工具是"万能选手"，不管得分高低都必须带上
# 比如知识库检索，很多场景都用得到
force_include = ["knowledge_retrieval", "web_search"]
for name in force_include:
    if name not in selected_tools:
        selected_tools.append(name)

# 如果工具总数少于 10 个，预筛选就不开启
# 这么少工具 LLM 自己就能选对，没必要加这层
if len(all_tools) <= 10:
    return all_tools  # 全部发给 LLM
```

### 2.5 代码实现流程（结果校验与自动重试）

#### 第一步：工具返回结果后，先过一道"安检"

```python
class ToolResultValidator:
    @staticmethod
    def validate(result):
        # 安检 1：是不是空结果？
        if result is None:
            return {"is_valid": False, "issue": "空结果", "suggestion": "换个关键词试试"}
        
        # 安检 2：是不是空列表/空字典？
        if isinstance(result, (list, dict)) and len(result) == 0:
            return {"is_valid": False, "issue": "没有匹配数据", "suggestion": "扩大检索范围"}
        
        # 安检 3：工具是不是报错了？
        if isinstance(result, str) and result.startswith("**ERROR**"):
            return {"is_valid": False, "issue": "工具报错", "suggestion": "跳过这个工具"}
        
        # 安检 4：结果是不是太长了？超过 50000 字符就截断
        if isinstance(result, str) and len(result) > 50000:
            return {"is_valid": True, "cleaned": result[:20000] + "...[已截断]"}
        
        return {"is_valid": True, "cleaned": result}
```

#### 第二步：如果安检没过，自动重试一次

```python
def execute_tool_with_retry(name, args):
    # 第 1 次执行
    result = toolcall_session.tool_call(name, args)
    
    # 过安检
    check = ToolResultValidator.validate(result)
    
    # 安检通过 → 直接返回
    if check["is_valid"]:
        return check["cleaned"]
    
    # 安检不通过 → 只重试一次
    # 比如检索没结果 → 加上"尝试同义词"再查一次
    corrected_args = {**args, "query": args["query"] + " 同义词"}
    retry_result = toolcall_session.tool_call(name, corrected_args)
    
    retry_check = ToolResultValidator.validate(retry_result)
    if retry_check["is_valid"]:
        return retry_check["cleaned"]
    
    # 重试还失败 → 返回空结果 + 说明，不给 LLM 看到原始错误
    return {"_note": f"工具返回 {check['issue']}，重试后仍未解决", "result": ""}
```

### 2.6 面试官可能会追问

**问："Top-5 筛漏了怎么办？用户要的工具不在里面。"**

> 如果真的不在，LLM 拿到 5 个不相关的工具，会尝试用它们去完成任务。比如用户要查 Jenkins 构建状态，但 Top-5 里没有 Jenkins 工具，LLM 可能会用知识库去搜"Jenkins 状态"。搜不到就会说"我没有这个权限"。这不是最理想的，但不会给错误答案。而且工具结果校验会把空结果拦截住，不会让 LLM 自己瞎编。

**问："工具描述写得好不好，影响大吗？"**

> 非常大。embedding 匹配的效果完全取决于描述质量。我们内部有个规范——工具描述必须写成"场景词 + 能力词 + 关键词"。比如"查询 Jira 工单状态、Assignee、Sprint 信息，支持按项目 Key 筛选"。如果只写"Jira 查询"，匹配效果就很差。所以这不是一个纯算法问题，还有工程规范问题。

## 三、层级化记忆管理

### 3.1 场景故事（一句话）

> **客服团队说："用户问退款到哪了，它去查了物流信息。明明之前说过是京东快递，它非按顺丰去查。"**
>
> 同时：
> **财务说："上个月 LLM 费用涨了 3 倍。"**

### 3.2 大白话讲问题

客服处理一个投诉需要 20-30 轮对话。前 5 轮用户说清楚了：订单号 12345、用的京东快递、已经等了 7 天。

到了第 15 轮，LLM 已经忘了"京东快递"这个信息。为什么？因为每次调用 LLM 时，会把所有历史消息都传过去。30 轮对话 + 20 次工具调用的结果，合起来可能超过 2 万个 Token。超过 LLM 的上下文窗口后，最早的那些消息就被截断了。

原来的做法是：超过 3 轮就全部压缩成一句话。但压缩完连"订单号 12345"这种关键信息也丢了。

### 3.3 大白话讲思路

之前的压缩方式是一刀切——不管三七二十一，超过 3 轮就全部压成一坨。我的做法是分层处理：

```
1-3 轮：不压，保留全部
4-10 轮：只压工具返回的详细数据（JSON 太长），保留对话主线和关键信息
10 轮以上：让 LLM 主动总结一下前面说了什么
```

同时，我还把记忆按类型分了类。这样检索时不会把不相关的信息带进来。

### 3.4 代码实现流程

#### 第一步：先算一下对话有多少轮

```python
def compress_memory(messages):
    # 数一数用户问了多少次问题
    total_rounds = len([m for m in messages if m["role"] == "user"])
```

#### 第二步：根据轮数选择压缩策略

```python
def compress_memory(messages):
    total_rounds = len([m for m in messages if m["role"] == "user"])
    
    # 先把系统提示词（system）单独拿出来，这个不能丢
    system_prompt = None
    if messages[0]["role"] == "system":
        system_prompt = messages[0]
        rest = messages[1:]  # 剩下的才是对话内容
    else:
        rest = messages
    
    # ─── Level 1：3 轮以内，不压缩 ───
    if total_rounds <= 3:
        return messages  # 原样返回
    
    # ─── Level 2：4-10 轮，只压工具结果 ───
    if total_rounds <= 10:
        compressed = []
        for msg in rest:
            if msg["role"] == "tool":
                # 工具返回结果通常是一大段 JSON
                # 只保留前 200 个字符
                content = msg.get("content", "")
                if len(content) > 200:
                    msg["content"] = content[:200] + "...[已压缩]"
            compressed.append(msg)
        result = compressed
    
    # ─── Level 3：10 轮以上，LLM 做摘要 ───
    else:
        # 把除了最后一轮之外的历史交给 LLM，让它总结
        summary = chat_mdl.chat("总结以下对话的核心信息", rest[:-1])
        result = [
            {"role": "system", "content": f"[历史摘要] {summary}"},
            rest[-1]  # 保留最后一轮用户问题
        ]
    
    # system prompt 放回开头
    if system_prompt:
        result.insert(0, system_prompt)
    return result
```

#### 第三步：把记忆分类存起来

这一步是额外的优化，和压缩是两回事。

```python
class StructuredMemory:
    def __init__(self):
        # 分了 5 个"盒子"放不同类型的记忆
        self.memories = {
            "factual": [],       # 事实：用户的地址、会员等级
            "preference": [],    # 偏好：喜欢简短回答
            "context": [],       # 上下文：刚才查了订单 12345
            "session": [],       # 会话：用户今天催了 3 次
            "task_status": [],   # 任务状态：退款流程已完成
        }
        self.pending = []  # 待处理的对话
```

#### 第四步：不每条对话都分类，攒够 5 条一起分

```python
    async def add(self, user_input, response):
        # 先把对话扔进待处理队列
        self.pending.append({"user": user_input, "assistant": response})
        
        # 攒够 5 条才处理一次
        if len(self.pending) >= 5:
            # 5 条打包成一段文本，让 LLM 一次性分类
            batch_text = "\n".join(f"User: {p['user']}\nAI: {p['assistant']}" for p in self.pending)
            
            classification = await llm.chat(
                "分析以下对话，提取信息并按类型归类。",
                batch_text
            )
            
            # LLM 返回：{"factual": ["用户地址在北京"], "context": [...], ...}
            # 按类型放进对应的盒子里
            for category, items in classification.items():
                self.memories[category].extend(items)
            
            self.pending = []  # 清空待处理队列
```

#### 第五步：检索时不用全量拼接，只取最相关的

```python
    async def get_relevant(self, query):
        # 用户问："退款到哪了？"
        # 全量拼接所有记忆 → 太长了浪费 Token
        # 我的做法：用 embedding 匹配，只取最相关的 3 条
        
        query_emb = embedding_model.encode(query)
        
        scored = []
        for category, items in self.memories.items():
            for item in items:
                item_emb = item["embedding"]  # 存记忆时就生成了 embedding
                score = cosine_similarity(query_emb, item_emb)
                scored.append((score, item))
        
        # 取前 3 条最相关的
        scored.sort(reverse=True)
        return scored[:3]
        
        # "退款到哪了" → 匹配到 task_state → "退款流程已完成，等待到账"
        # 不会匹配到 factual → "用户地址在北京"
```

### 3.5 面试官可能会追问

**问："3 轮和 10 轮这个阈值怎么定的？有理论依据吗？"**

> 没有特别严谨的理论依据，是从客服场景的对话数据里观察出来的。1-3 轮在聊同一个子问题，4-10 轮开始出现工具调用，10 轮以上 LLM 开始遗忘早期信息。这些阈值我设计成了可配置参数，不同场景可以调。

**问："5 条对话才分类一次，会不会有延迟？"**

> 会有短暂的延迟，但影响不大。因为我们存的是"结构化的知识"（比如"用户是铂金会员"这种相对固定的信息），不是"对话流水账"。就算晚几轮才存进去，也不会影响当前回答的质量。

## 四、运行时动态装配

### 4.1 场景故事（一句话）

> **开发同事说："运营那边想加一个新工具——查企业微信通讯录。我改完代码发版，重启服务，研发那边正好在用，服务断了 2 分钟，被骂了。"**
>
> 同时：
> **"财务那边说 Jira 查询工具有 Bug——查不到已关闭的工单。我修好了发布新版，但已经在运行的 Agent 怎么用上新版？"**

### 4.2 大白话讲问题

最开始的时候，Agent 用的所有工具都是写死在代码里的。比如：

```python
tools = [JiraTool(), GitLabTool(), KnowledgeTool(), ...]
```

如果运营想要加一个新工具，开发就得改代码、发版、重启服务。重启就意味着正在用 Agent 的人会断连。

而且工具修了 Bug 之后也没办法通知已经在运行的 Agent——它用的还是旧版本的代码。

### 4.3 大白话讲思路

我的做法是：**不把工具写死在代码里，而是存在 Redis 里。Agent 每次启动时从 Redis 拉取最新的工具列表。**

这就像开饭店：

```
原来的做法：
  菜单是印在墙上的 → 想换菜？得把墙砸了重新刷
  
我的做法：
  菜单写在黑板上的 → 想换菜？擦了重写就行
  Agent 是服务员 → 客人来了先看黑板，今天有什么菜就做什么
```

### 4.4 代码实现流程

#### 第一步：工具信息不放代码里，放 Redis

```python
# 以前是这样写的：
# tools = [JiraTool(), GitLabTool(), KnowledgeTool()]

# 现在改成存在 Redis 里：
# Redis key: "agent_tool:jira_tool"
# {
#   "class_path": "agent.tools.custom.JiraTool",  # 类的路径
#   "version": "v2",                                # 版本号
#   "description": "查询 Jira 工单状态"             # 描述
# }
#
# Redis key: "agent_tool:gitlab_tool"
# {
#   "class_path": "agent.tools.custom.GitLabTool",
#   "version": "v1",
#   "description": "搜索 GitLab 代码仓库"
# }
#
# 还有一个 Set 叫 "agent_tools:active"，记录了当前有哪些工具可用
# {"jira_tool", "gitlab_tool", "knowledge_tool", ...}
```

#### 第二步：Agent 启动时，从 Redis 拉取工具

```python
class DynamicToolRegistry:
    def __init__(self, redis):
        self.redis = redis
        self.cache = {}  # 本地缓存，减少 Redis 查询
    
    async def load_for_agent(self):
        # 1. 从 Redis 获取所有可用的工具名
        active_tools = await self.redis.smembers("agent_tools:active")
        # 返回：{"jira_tool", "gitlab_tool", "knowledge_tool", ...}
        
        tools = {}
        for name in active_tools:
            # 2. 获取每个工具的元信息（类路径、版本号）
            meta = await self.redis.hgetall(f"agent_tool:{name}")
            
            # 3. 通过 importlib 导入工具类
            # importlib 是 Python 自带的库，可以根据字符串导入模块
            module_path, class_name = meta["class_path"].rsplit(".", 1)
            # "agent.tools.custom.JiraTool" → module="agent.tools.custom", class="JiraTool"
            
            module = importlib.import_module(module_path)
            tool_cls = getattr(module, class_name)
            
            # 4. 实例化工具
            tools[name] = tool_cls()
            
            # 5. 缓存起来，下次就不用查 Redis 了
            self.cache[name] = {"class": tool_cls, "version": meta["version"]}
        
        return tools
```

#### 第三步：新增工具时，只需写入 Redis

```python
# 运营想要加一个"查企业微信通讯录"的工具
# 开发写好了 WeChatTool 类，然后执行：
await registry.register(
    name="wechat_tool",
    class_path="agent.tools.custom.WeChatTool",
    version="v1",
    description="查询企业微信通讯录"
)

# register 方法做了 3 件事：
# 1. 把工具信息写入 Redis Hash
await redis.hset("agent_tool:wechat_tool", mapping={
    "class_path": "agent.tools.custom.WeChatTool",
    "version": "v1",
    "description": "查询企业微信通讯录"
})

# 2. 把工具名加入活跃列表
await redis.sadd("agent_tools:active", "wechat_tool")

# 3. 通过 Pub/Sub 通知所有在运行的 Agent
await redis.publish("agent_tools:changes", "wechat_tool")
# → 所有 Agent 收到通知后，清除本地缓存
# → 下一个请求进来时，会重新从 Redis 加载工具列表
# → 自动拿到新工具
```

#### 第四步：版本更新时，不影响正在执行的请求

```python
# 假设 Jira 工具修了一个 Bug，从 v1 升级到 v2

# 步骤 1：注册 v2 版本（v1 还在）
redis.hset("agent_tool:jira_tool:v2", mapping={
    "class_path": "agent.tools.custom.JiraToolV2",
    "version": "v2"
})

# 步骤 2：把活跃版本切换到 v2
redis.set("agent_tool:jira_tool:active", "v2")

# 步骤 3：通知所有 Agent
redis.publish("agent_tools:changes", "jira_tool")

# 关键点：正在用 v1 执行请求的 Agent 实例不受影响
# 它持有的还是 v1 的工具引用
# 等当前请求执行完，Agent 收到通知，清除缓存
# 下次请求来的时候，重新加载的是 v2
```

#### 第五步：出 Bug 了？秒级回滚

```python
# 发现 v2 有 Bug，回滚到 v1
redis.set("agent_tool:jira_tool:active", "v1")
redis.publish("agent_tools:changes", "jira_tool")
# Agent 收到通知 → 清除缓存 → 下次请求加载 v1
# 整个过程对用户无感
```

### 4.5 面试官可能会追问

**问："为什么不用 pickle 序列化？"**

> 这是安全考虑。Pickle 反序列化时可以执行任意代码。如果被人拿到了 Redis 的权限，往里面放一个恶意 pickle，服务器就被人控制了。Importlib 只能在 Python 的模块路径下导入，安全得多。

**问："Agent 怎么感知到 Redis 里的变化？"**

> 通过 Redis 的 Pub/Sub（发布订阅）。新增或更新工具时，会通过 Redis 发一条消息。Agent 启动了一个后台任务在监听这些消息。收到消息后，Agent 不会立即重新加载（因为当前请求还在用旧版本），而是清除本地缓存，等当前请求处理完，下次请求时自动加载最新版本。

## 五、面试时的讲述策略

### 5.1 按这个顺序讲

```
项目是什么：企业内部 AI 知识问答与任务执行平台

第一版：纯 RAG → 只有问答
  ↓ 用户说"能不能帮我查个 Jira 工单"（用户需求推动）
第二版：Agent + ReAct → 能调工具了
  ↓ 运营说"帮我写事故报告，你咋只分析了一个 Bug"（业务痛点推动）
第三版：Plan-then-Execute → 先规划再执行
  ↓ 运营又说"我让你查 Jira 你去查知识库"（工程问题推动）
第四版：工具预筛选 → 只发 5 个给 LLM
  ↓ 运营还说"你查到了但链接是空的"（另一个工程问题推动）
第五版：结果校验 → 空结果自动重试
  ↓ 客服说"之前说过的它又忘了"（新场景推动）
第六版：三级压缩 + 结构化记忆 → 长对话优化
  ↓ 开发说"每次加个工具都要重启被骂了"（运维问题推动）
第七版：动态装配 → Redis 热加载
```

### 5.2 核心原则

每个改造点的开头都是：**"后来遇到了一个问题……"**

面试官听完会觉得你不是在背技术方案，而是在讲一个真实的故事。这个故事里的每一个改动都有前因后果，不是拍脑袋想出来的。
