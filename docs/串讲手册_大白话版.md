## 一、Plan-then-Execute 混合推理架构

### 1.1 场景故事（一句话）

> **运营同事说："帮我写一份上周的线上事故报告，包含事故数量、影响范围、处理进度。"**
>
> 然后 Agent 开始干活——先查 Jira、再查 GitLab、再查值班表……干了 10 轮，最后输出了一份报告，但报告里只分析了某一个 Bug，完全忘了最初要的是"整体报告"。

### 1.2 大白话讲问题

原来的 Agent 工作方式是**走一步看一步**。就像你让一个实习生去写报告，他不先想好要查什么、从哪查，而是查到一个数据就开始分析，分析到一半发现还得查另一个数据，查完回来已经忘了最初要干嘛了。

LLM 也是这样。每轮只看到当前工具返回的结果，很容易被中间信息带偏。

而且随着公司越来越多部门接入，问题变得更复杂了：

```
财务部问："帮我分析 Q2 华东区营收"
  → Agent 跑去查了 GitLab 代码仓库……财务连 GitLab 是什么都不知道

运营部问："写一份事故复盘报告"
  → Agent 第一轮去查了知识库，第二轮去查了 Jira
  → 第三轮突然去查了天气 API（？）
  → 它调了一个不在授权范围内的工具，没人发现
```

这就暴露了两个问题：
1. **不同部门看到的工具集应该不一样**——财务不该看到 GitLab，研发不该看到 ERP
2. **计划里提到的工具必须是真实存在的**——不能让 LLM 自己编一个工具名

### 1.3 大白话讲思路

我的做法是给原来的"先计划再执行"加了一层"前置处理"和一层"后置审查"，变成了一个完整的 6 步流程：

```
用户提问
  │
  ▼
① 场景分类 → 确定用哪组工具（财务/研发/运营）
  │
  ▼
② 生成执行计划（带上可用工具清单，输出 JSON）
  │
  ▼
③ 校验计划（格式、工具存在性、逻辑依赖）
  │
  ▼
④ 逐步执行（带缓存 + 结果快速检查 + 高风险操作暂停确认）
  │
  ▼
⑤ 汇总草稿 + 可信度审查
  │
  ▼
⑥ 输出最终答案（或低分时追问用户）
```

每一步都不动原有的 ReAct 循环，只是在外面加包装层。

### 1.4 代码实现流程（大白话版）

#### 第一步：用户提问 → 先判断场景，缩小工具范围

```python
# 用户说："帮我分析 Q2 华东区营收对比"
#
# 原来的做法：所有 20 个工具都摆出来让 LLM 选
# 我的做法：先判断这是哪个业务线的问题，只给对应的工具

# ① 轻量级场景分类
# 用一个简单的 Prompt 让 LLM 判断场景
scene_prompt = """
根据用户问题判断所属场景，只输出一个词：
财报分析 / 事故复盘 / 客户投诉 / 合同审查 / 通用问答
"""
scene = await llm.chat(scene_prompt, user_query)
# 返回："财报分析"

# ② 根据场景路由到对应的工具子集
tool_router = {
    "财报分析": ["财报检索", "SQL查询", "趋势绘图"],
    "事故复盘": ["知识库检索", "Jira查询", "GitLab查询", "报告模板库"],
    "客户投诉": ["CRM查询", "工单系统", "邮件发送"],
    "合同审查": ["文档解析", "条款比对", "法规库"],
    "通用问答": ["通用搜索", "知识库检索"]
}
available_tools = tool_router.get(scene, ["通用搜索"])

# 企业价值：
# - 财务看不到 GitLab，研发看不到 ERP，安全
# - LLM 收到的工具描述少了，选错概率降低
# - Prompt 里的 Token 消耗减少
```

#### 第二步：带着工具清单生成计划（JSON 格式）

```python
# 原来的计划 Prompt 是自由文本格式
# 改成严格 JSON 格式，每步必须绑定一个工具

plan_prompt = f"""
你是一个企业智能助手，当前可用的工具只有：{available_tools}
请根据用户问题，生成一个多步骤执行计划，
每一步都必须明确使用哪个工具。

输出 JSON 数组格式（不要输出其他内容）：
[
  {{"step": 1, "tool": "工具名", "action": "执行描述"}},
  {{"step": 2, "tool": "工具名", "action": "执行描述"}}
]

最多不超过 8 步。
如果无法规划，输出 [] 。
"""

plan = await llm.chat(plan_prompt, user_query)
# LLM 返回（JSON 格式）：
# [
#   {"step": 1, "tool": "财报检索", "action": "获取2024Q2营收明细"},
#   {"step": 2, "tool": "SQL查询", "action": "计算华东区环比增长率"},
#   {"step": 3, "tool": "趋势绘图", "action": "生成营收趋势图"}
# ]

# JSON 格式的好处：可以直接用代码解析，不需要正则匹配
import json
plan_steps = json.loads(plan)  # 一步到位
```

#### 第三步：三层计划校验

```python
class PlanValidator:
    def __init__(self, available_tools):
        self.tool_set = set(available_tools)
        # 工具依赖规则：从工具元数据中读取，不硬编码
        # 比如"趋势绘图"注册时声明了 depends_on=["SQL查询"]
        # 这样不同部门的依赖规则可以不同，不用改代码
        self.dependency_rules = self._load_dependency_rules(available_tools)
    
    def validate(self, plan_steps):
        # 第一层：基础格式检查
        if not isinstance(plan_steps, list) or len(plan_steps) == 0:
            return False, "计划为空或格式错误"
        if len(plan_steps) > 8:
            return False, "步骤数超过上限 8"
        
        # 第二层：工具存在性检查（硬拦截）
        for step in plan_steps:
            tool_name = step.get("tool", "")
            if tool_name not in self.tool_set:
                # 这是硬拦截——LLM 想调用一个不存在的工具
                # 直接拒绝，要求重新生成
                return False, f"步骤 {step['step']} 使用了未授权的工具 '{tool_name}'"
        
        # 第三层：工具依赖逻辑检查
        # 比如"趋势绘图"依赖"SQL查询"先执行
        # 这个依赖关系是工具注册时自己声明的，不是写死的
        for step in plan_steps:
            tool_name = step["tool"]
            if tool_name in self.dependency_rules:
                required_tools = self.dependency_rules[tool_name]
                preceding = [s["tool"] for s in plan_steps if s["step"] < step["step"]]
                for req in required_tools:
                    if req not in preceding:
                        return False, f"步骤 {step['step']} ({tool_name}) 依赖 {req} 先执行"
        
        return True, "校验通过"

# 企业价值：  
# - 工具存在性检查是"硬拦截"——不存在的工具直接报错
# - 依赖规则从工具自身的元数据读取，不是硬编码字典
#   新增工具时只需要在工具注册时声明依赖关系
```

#### 第四步：逐步执行（缓存 + 结果验证 + 高风险确认）

这是整个流程的核心。每执行一步做三件事。

```python
# ① 请求级缓存：相同工具+相同参数不重复调用
cache = {}  # 这个缓存只在当前请求生命周期内有效

async def execute_with_cache(tool_name, action_params):
    # 用工具名+参数做一个稳定的缓存 key
    # action_params 是结构化参数（dict），不是字符串
    # 所以要先序列化再 hash
    import hashlib
    raw_key = f"{tool_name}:{json.dumps(action_params, sort_keys=True)}"
    cache_key = hashlib.md5(raw_key.encode()).hexdigest()
    
    if cache_key in cache:
        print(f"命中缓存，跳过执行: {tool_name}")
        return cache[cache_key]
    
    result = await call_tool(tool_name, action_params)
    cache[cache_key] = result
    return result


# ② 步骤结果快速验证
# 不同工具类型有不同的"成功"标准，在工具注册时声明
# 比如：检索类工具要求 chunks 不为空
#       SQL查询要求返回列表不为空
def check_step_result(tool_name, result):
    rules = {
        "财报检索": lambda r: len(r.get("chunks", [])) > 0,
        "SQL查询": lambda r: isinstance(r, list) and len(r) > 0,
        "知识库检索": lambda r: len(r.get("chunks", [])) > 0,
    }
    checker = rules.get(tool_name)
    if checker and not checker(result):
        return False, f"{tool_name} 返回空结果，请调整查询条件重试"
    return True, ""


# ③ 高风险操作的人工确认
# 有些操作不能自动执行，需要用户点头
HIGH_RISK_TOOLS = ["邮件发送", "工单创建", "数据库写入"]

async def execute_plan(plan_steps, on_confirm=None):
    completed = []
    for step in plan_steps:
        tool_name = step["tool"]
        action = step["action"]
        
        # 风险操作确认
        if tool_name in HIGH_RISK_TOOLS and on_confirm:
            # 发出确认请求，等待用户回复
            confirmed = await on_confirm(f"即将执行 {tool_name}: {action}，是否继续？")
            if not confirmed:
                completed.append(f"步骤 {step['step']} ({tool_name}) 已被用户取消")
                continue
        
        # 执行（带缓存）
        result = await execute_with_cache(tool_name, {"query": action})
        
        # 结果验证
        valid, msg = check_step_result(tool_name, result)
        if not valid:
            # 一次自我纠错机会：把错误信息给 LLM，让它改参数重试
            corrected = await llm.chat(
                f"上一步执行失败：{msg}，请给出修正后的查询参数",
                {"tool": tool_name, "original": action}
            )
            result = await execute_with_cache(tool_name, corrected)
        
        completed.append(result)
    
    return completed
```

#### 第五步：汇总 + 可信度审查（一次 LLM 调用完成）

```python
# 所有步骤执行完后，生成最终回答并做可信度检查
# 原来：先生成 → 再审查 → 再追问（3 次 LLM 调用）
# 优化后：一次 LLM 调用同时生成回答和可信度评分

final_prompt = f"""
你是一个企业智能助手。以下是根据用户问题执行各步骤后得到的结果。

用户问题：{user_query}
各步骤产出：{completed_contexts}

请完成两项工作：
1. 根据以上信息生成最终回答
2. 对回答的可信度进行评分（0-1），考虑以下因素：
   - 步骤执行是否全部成功
   - 数据是否完整
   - 推理逻辑是否自洽

输出 JSON 格式：
{{
  "answer": "最终回答内容",
  "confidence": 0.85,
  "issues": ["步骤2返回的数据不完整，结论可能不准确"]
}}
"""

result = await llm.chat(final_prompt)

if result["confidence"] < 0.5:
    # 低可信度 → 不直接回答，转为追问
    clarifying = f"根据当前获取到的信息，我还无法给出可靠回答。{result['issues'][0] if result['issues'] else ''}，请补充更多信息。"
    yield {"type": "clarify", "question": clarifying}
else:
    # 高可信度 → 输出带置信度的回答
    confidence_badge = f"\n\n（本回答可信度：{result['confidence']*100:.0f}%）"
    yield result["answer"] + confidence_badge
```

### 1.5 完整流程总结

加上上述增强后，Plan-then-Execute 变成了一个完整的 6 阶段流程：

```
用户提问
  │
  ▼
① 场景分类 + 工具路由
   ├── 轻量 LLM 判断场景（财报/事故/投诉/合同/通用）
   └── 根据场景选择工具子集（安全隔离 + Token 节省）
  │
  ▼
② 工具感知的计划生成（JSON 格式）
   ├── Prompt 中明确列出可用工具
   └── 每步必须绑定一个具体工具
  │
  ▼
③ 三层计划校验
   ├── 格式检查（JSON 解析、步骤数量）
   ├── 工具存在性硬拦截（不存在的工具直接拒绝）
   └── 依赖逻辑检查（从工具元数据读取，非硬编码）
  │
  ▼
④ 逐步执行循环
   ├── 请求级缓存（相同工具+参数不重复调用）
   ├── 结果快速验证（根据工具类型检查结果是否有效）
   ├── 一次自我纠错（无效结果让 LLM 改参数重试）
   └── 高风险操作人工确认（发邮件/创建单需要用户点头）
  │
  ▼
⑤ 汇总草稿 + 置信度评估（一次 LLM 调用）
   ├── 同时生成回答和可信度评分
   └── 低分（<0.5）自动转为追问，不输出不可靠回答
  │
  ▼
⑥ 输出最终答案（带可信度标记）
```

和原来相比，核心变化是：

| 维度 | 原来的 Plan-then-Execute | 增强后 |
|------|------------------------|--------|
| 工具范围 | 全部工具 | 按场景路由的子集 |
| 计划格式 | 自由文本 | JSON（可直接解析） |
| 工具校验 | 警告但不阻断 | 硬拦截 + 依赖检查 |
| 执行效率 | 每步都调 LLM | 缓存去重 |
| 结果可靠性 | 透传工具结果 | 验证 + 自我纠错 |
| 安全性 | 无 | 高风险操作确认 |
| 输出可信度 | 无 | 置信度评分 + 低分追问 |

### 1.6 面试官可能会追问

**问："场景分类又多了一次 LLM 调用，成本怎么控制？"**

> 这个分类用的是一次极简的 LLM 调用——Prompt 只有几十个 Token，模型用最快的（比如 GPT-4o-mini），单次成本可以忽略不计。而且它带来的好处远大于成本：一方面过滤掉了无关工具，后续每次 LLM 调用的 Token 都减少了；另一方面防止了跨部门工具越权，这是安全收益，不能用成本衡量。

**问："JSON 格式的计划如果 LLM 输出格式不对怎么办？"**

> 分两种情况：如果是少量格式错误（比如多了一个逗号），我用 `json_repair` 库自动修复。如果是完全乱来（比如输出了散文而不是 JSON），PlanValidator 会检测到格式错误，要求 LLM 重新生成，最多重试 2 次。实测中 GPT-4 级别的模型按这个 Prompt 输出 JSON 的成功率在 99% 以上。

**问："工具依赖规则写死在代码里，新工具接入不是很麻烦？"**

> 依赖规则不是硬编码的。每个工具注册时可以在元数据里声明 `depends_on` 字段，PlanValidator 启动时从工具注册中心读取。这样新增工具时只需要在注册信息里写清楚依赖关系，不需要改 PlanValidator 的代码。

**问："置信度评分让 LLM 自己给自己打分，会不会不客观？"**

> 这个问题问得好。我主要用它来捕捉**明显的失败场景**——比如某步骤返回了空结果、某个工具报错了。这些情况下 LLM 自己也知道数据不可靠，confidence 会打得很低。对于"数据看起来都对但其实是错的"这种情况（比如 LLM 幻觉），置信度评分确实不一定能发现。所以我的策略是：**低分直接拦截（精确率高），高分不保证绝对正确，但至少让使用者知道风险。** 加了置信度标记之后，运营团队反馈说"看到 90% 以上的回答我们就直接用了，低于 60% 的我们会复查一下"。

## 二、智能工具编排系统

### 2.1 场景故事（一句话）

> **运营同事说："我让它查一个 Jira 工单，它去查了知识库，浪费了好几分钟。"**
>
> 同时：
> **运营同事又说："它说查到了事故记录，但点开链接是空的。"**
>
> 再后来：
> **安全同事说："运营部的人怎么能调用 GitLab 的代码接口？权限谁管的？"**
>
> 再再后来：
> **运维同事说："那个 Jira 接口下午挂了 10 分钟，Agent 一直在疯狂重试，把下游都打崩了。"**

### 2.2 大白话讲问题

项目接入了 20 多个业务系统：Jira、GitLab、知识库、值班表、Jenkins……每次用户提问时，我们把 20 个工具的说明书全部发给 LLM，让 LLM 自己选用哪个。但这引发了 4 个层面的问题：

**第一层：效率问题**
20 个工具定义占 8000+ Token，LLM 光读说明书就消耗了大量上下文。

**第二层：准确性问题**
工具多，LLM 容易选错。"查 Jira 工单" → LLM 去调了知识库。因为知识库的描述里也提到了"工单"两个字。

**第三层：权限问题**
运营部的人理论上只能看到客服相关的工具，但在当前系统里，他们能看到 GitLab、Jenkins 这些研发工具。虽然不是故意的，但数据泄露的风险摆在那里。

**第四层：稳定性问题**
工具是不可靠的。有时候 Jira 挂了、有时候网络超时、有时候返回空结果。更糟的是——如果 Agent 发现工具挂了，它会拼命重试，把本来就脆弱的接口打得更死。

### 2.3 大白话讲思路

原来的流程是：

```
用户提问 → 所有工具发给 LLM → LLM 选 → 调用 → 结果给 LLM
```

这个流程在 4 个层面都有漏洞。我把它改造成了：

```
用户提问
  │
  ▼
① 预筛选阶段（4 层过滤）
   ├── 健康检查：已经挂了的工具直接排除 → 不会选到宕机工具
   ├── 权限过滤：用户没有权限的工具直接排除 → 安全合规
   ├── 语义匹配：计算问题与工具的语义相似度 → 保证相关性
   └── 规则加权：命中业务标签的工具提高分数 → 兜底语义偏差
  │
  ▼
② 筛选后只留 Top-5（+ 强制兜底工具）
  │
  ▼
③ 调用阶段
   ├── 熔断检查：近期频频失败的工具直接跳过 → 防止雪崩
   ├── 结果校验 + 分级重试：不同错误不同处理 → 提高恢复率
   └── 用户隔离缓存：相同请求不重复调下游 → 减负
  │
  ▼
④ 审计日志：每次调用都记录 → 可追溯
```

每一步都只增加了少量代码，但解决了企业落地中的效率、安全、稳定、可追溯四大问题。

### 2.4 预筛选阶段：4 层过滤

#### 第一层：工具健康检查

```python
# 每个工具注册时附带一个健康检查接口，Agent 定期 ping
# 健康状态存在 Redis 里，TTL 30 秒

class HealthChecker:
    def __init__(self, redis):
        self.redis = redis
    
    async def get_healthy_tools(self, all_tools):
        healthy = []
        for name in all_tools:
            # 从 Redis 读取健康状态
            status = await self.redis.get(f"tool_health:{name}")
            if status == "healthy" or status is None:
                # status 为 None 表示还没检查过，默认健康

            else:
                logging.warning(f"工具 {name} 已被健康检查排除")
        return healthy
    
    async def report_failure(self, name):
        # 工具调用失败时，记录失败次数
        key = f"tool_health:{name}"
        fails = await self.redis.incr(f"{key}:fails")
        if fails >= 3:  # 连续失败 3 次标记为不健康
            await self.redis.set(key, "unhealthy", ex=30)  # 30 秒后自动恢复
            await self.redis.delete(f"{key}:fails")

# 企业价值：接口宕机时不硬调用，不浪费 LLM 轮次，不加重下游负担
```

#### 第三层：语义匹配 + 业务标签加权

```python
# 原来的语义匹配是纯 embedding 相似度
# 现在加上业务标签加权作为规则兜底

class ToolScorer:
    def __init__(self):
        # 每个工具可以打多个业务标签
        self.tool_tags = {
            "Jira查询": ["工单", "Bug", "任务"],
            "CRM查询": ["客户", "合同"],
            "GitLab查询": ["代码", "MR", "分支"],
            "知识库检索": ["文档", "知识", "FAQ"],
            "Jenkins查询": ["构建", "流水线", "部署"],
        }
    
    def score(self, tool_name, query_embedding, tool_embedding, user_query):
        # 基础分：语义相似度
        semantic_score = cosine_similarity(query_embedding, tool_embedding)
        
        # 加分：命中业务标签
        tags = self.tool_tags.get(tool_name, [])
        tag_bonus = 0
        for tag in tags:
            if tag.lower() in user_query.lower():
                tag_bonus += 0.15  # 每个命中标签加 0.15
        
        final_score = semantic_score + tag_bonus
        return final_score

# 企业价值：语义匹配+规则兜底，两种手段互补
# 比如查"工单" → 语义可能匹配到"工单系统"(0.7) 和 "CRM"(0.6)
#   加上标签加权后 → "工单系统"(0.7+0.15=0.85) 明显高于 CRM(0.6)
#   排序更准确
```

#### 第四层：强制兜底工具 + 小工具集跳过

```python
def finalize_tool_selection(scores, all_tools, user_role):
    # 规则 1：小工具集跳过筛选
    if len(all_tools) <= 10:
        return all_tools  # 工具少，LLM 自己就能选对，不筛了
    
    # 规则 2：按分数排序取 Top-5
    scores.sort(key=lambda x: x[1], reverse=True)
    selected = [s[0] for s in scores[:5]]
    
    # 规则 3：强制兜底工具
    # 不管语义得分高低，这些工具永远在候选名单里
    # 因为它们是"万能选手"，很多场景都用得到
    force_include = {
        "*": ["知识库检索", "通用搜索"],  # 所有用户都强制包含
        "developer": ["知识库检索"],       # 研发额外强制包含
    }
    for tool in force_include.get("*", []):
        if tool not in selected:
            selected.append(tool)
    for tool in force_include.get(user_role, []):
        if tool not in selected:
            selected.append(tool)
    
    return selected
```

### 2.5 工具调用阶段：熔断 + 分级重试 + 缓存

#### 第一步：重试上限保护（替代熔断器）

```python
# 熔断器（Circuit Breaker）是微服务架构里的标准模式，
# 但在 Agent 工具调用场景下，如果一天只有几百次调用，
# 熔断条件很难触发，属于“看起来牛但实际用不上”的功能。
#
# 所以我没有实现完整的熔断器，而是做了一个更务实的：
# 重试上限保护 —— 单个工具连续失败 N 次后，不再重试，
# 直接返回"工具暂时不可用"，等下一次请求再试。

class RetryGuard:
    """
    重试上限保护：防止 Agent 在工具已经挂了的情况下还拼命重试
    
    和熔断器的区别：
    - 熔断器：维护 CLOSED/OPEN/HALF_OPEN 三态，逻辑完整但复杂
    - 重试上限保护：只记失败次数，超过阈值不再重试，简单可靠
    """
    
    def __init__(self, redis):
        self.redis = redis
        self.max_retries = 3  # 连续失败 3 次就不再重试
    
    async def should_retry(self, tool_name):
        key = f"retry_guard:{tool_name}:fails"
        fails = int(await self.redis.get(key) or 0)
        if fails >= self.max_retries:
            logging.warning(f"工具 {tool_name} 已连续失败 {fails} 次，跳过重试")
            return False
        return True
    
    async def record_failure(self, tool_name):
        key = f"retry_guard:{tool_name}:fails"
        await self.redis.incr(key)
        await self.redis.expire(key, 60)  # 1 分钟后自动重置
    
    async def record_success(self, tool_name):
        await self.redis.delete(f"retry_guard:{tool_name}:fails")

# 适用场景说明：
# - 如果下游接口经常挂（比如每天都有超时），可以升级为完整的熔断器
# - 如果下游接口基本稳定（偶尔超时），重试上限保护就够用了
# - 这套逻辑总共不到 30 行，随时可以升级
```

#### 第二步：区分可重试与不可重试错误

```python
class ErrorClassifier:
    """
    错误分类器：区分"值得重试"和"重试也没用"的错误
    
    可重试（值得自动修复）：
    - 空结果：数据源正常，但查询条件需要调整
    - 超时：网络波动，再试一次可能就通了
    - 服务端报错（5xx）：服务器压力大，等待后可能恢复
    
    不可重试（直接返回失败）：
    - 权限不足：重试 100 次也没权限
    - 参数格式错误：入参本身就是错的
    - 配额耗尽：等额度刷新才有用
    - 资源不存在：404 就是 404
    """
    
    RETRYABLE = {"EMPTY_RESULT", "TIMEOUT", "SERVER_ERROR"}
    FATAL = {"PERMISSION_DENIED", "INVALID_ARGUMENT", "QUOTA_EXCEEDED", "NOT_FOUND"}
    
    @staticmethod
    def classify(error_code, error_msg):
        if error_code in ErrorClassifier.RETRYABLE:
            return "retryable"
        if error_code in ErrorClassifier.FATAL:
            return "fatal"
        return "unknown"

# 企业价值：不给没意义的错误浪费一次 LLM "自我纠错"的调用
```

#### 第三步：分级退避重试策略

```python
class RetryStrategy:
    """
    分级退避重试：不同错误用不同手段
    
    空结果 → 放宽过滤条件，模糊搜索
    超时   → 指数退避等待（1s → 2s → 4s）
    服务端报错 → 固定等待 3 秒后直接重试
    """
    
    @staticmethod
    def get_retry_args(error_type, original_args, attempt):
        if error_type == "EMPTY_RESULT":
            # 空结果：放宽条件，模糊搜索
            query = original_args.get("query", "")
            return {
                **original_args,
                "query": f"{query} OR 同义词 OR 相近词",
                "fuzzy": True  # 开启模糊匹配
            }
        
        elif error_type == "TIMEOUT":
            # 超时：指数退避
            wait = 2 ** attempt  # 1s → 2s → 4s
            time.sleep(wait)
            return original_args  # 参数不变，直接重试
        
        elif error_type == "SERVER_ERROR":
            # 服务端报错：固定等待
            time.sleep(3)
            return original_args
        
        return original_args  # 兜底：参数不变重试


# ====== 整合后的调用逻辑 ======
async def execute_tool_with_protection(tool_name, args, circuit_breaker, user_id):
    # 1. 熔断检查
    if not await circuit_breaker.can_call(tool_name):
        return {"_error": "工具暂时不可用（熔断中）", "result": ""}
    
    # 2. 缓存检查
    cache_key = f"{tool_name}:{user_id}:{hashlib.md5(json.dumps(args).encode()).hexdigest()}"
    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)
    
    # 3. 第一次调用
    try:
        result = await toolcall_session.tool_call_async(tool_name, args)
        await circuit_breaker.record_success(tool_name)
    except Exception as e:
        error_type = classify_error(e)
        
        if error_type == "fatal":
            # 致命错误：直接返回，不重试
            await circuit_breaker.record_failure(tool_name)
            return {"_error": f"工具调用失败（{error_type}）", "result": ""}
        
        # 可重试错误：分级退避重试，最多重试 2 次
        for attempt in range(2):
            retry_args = RetryStrategy.get_retry_args(error_type, args, attempt)
            try:
                result = await toolcall_session.tool_call_async(tool_name, retry_args)
                await circuit_breaker.record_success(tool_name)
                break
            except Exception as retry_e:
                error_type = classify_error(retry_e)
                if error_type == "fatal":
                    await circuit_breaker.record_failure(tool_name)
                    return {"_error": f"工具调用失败（{error_type}）", "result": ""}
                continue
        else:
            # 重试全部失败
            await circuit_breaker.record_failure(tool_name)
            return {"_error": f"工具重试 2 次后仍然失败", "result": ""}
    
    # 4. 写缓存（TTL 5 分钟，带上用户 ID）
    await redis.setex(cache_key, 300, json.dumps(result))
    
    # 5. 审计日志
    await AuditLogger.log(tool_name, args, result, user_id, success=True)
    
    return result
```

#### 第四步：结构化审计日志

```python
class AuditLogger:
    """
    每次工具调用都记录结构化日志
    
    记录内容：
    - 谁调的（用户 ID、角色）
    - 调了什么（工具名、入参）
    - 结果如何（出参摘要、耗时、成功/失败）
    - 什么时候（时间戳）
    
    用途：
    - 安全审计："上周谁调了 GitLab 接口？"
    - 成本分析："哪个工具消耗了最多的 API 额度？"
    - 故障排查："这次调用为什么失败了？"
    """

    @staticmethod
    async def log(tool_name, args, result, user_id, success, duration_ms):
        log_entry = {
            "timestamp": datetime.now().isoformat(),
            "user_id": user_id,
            "tool_name": tool_name,
            "args_summary": truncate(str(args), 200),
            "result_summary": truncate(str(result), 500),
            "duration_ms": duration_ms,
            "success": success,
        }
        # 写本地日志文件（按天滚动），不依赖 ES/ClickHouse
        # 小规模用文件足够，哪天真的需要集中检索了再升级
        log_line = json.dumps(log_entry, ensure_ascii=False)
        logging.info(f"[AUDIT] {log_line}")
        # 同时写入 Redis 队列，方便实时查看最近 1000 条
        await redis.lpush("audit_log:recent", log_line)
        await redis.ltrim("audit_log:recent", 0, 1000)
```

### 2.7 面试官可能会追问

**问："权限过滤放在预筛选阶段，如果用户角色变了怎么办？"**

> 权限矩阵存在数据库里，每次请求时从 Token 解析当前角色，然后从 DB 拉取该角色的工具列表。角色变更后，下次请求自动生效，不需要重启。至于调用过程中的权限变更——理论上不会发生，因为一次请求通常只有几秒钟。

**问："重试上限到了之后，用户问的问题刚好需要这个工具，怎么办？"**

> 工具返回"暂时不可用"后，LLM 会自行决定如何处理——比如改用知识库检索代替实时查询，或者直接告诉用户"该功能暂时不可用"。这比让用户干等超时好得多。而且上限是 1 分钟自动重置的，不会永久禁用工具。

**问："缓存带了用户 ID，同一个部门的人查相同的内容不是浪费吗？"**

> 这是一个取舍。带上用户 ID 后缓存命中率确实会降低，但可以保证数据隔离——财务部的报表数据不会因为缓存命中而送到运营部手上。对于部门内共享的场景，可以额外加一层"团队缓存"：先查用户级缓存，没命中再查团队级缓存，都没命中才调下游。这在代码里多一层查询而已。

## 三、层级化记忆管理

### 3.1 场景故事（一句话）

> **客服团队说："用户问退款到哪了，它去查了物流信息。明明之前说过是京东快递，它非按顺丰去查。"**
>
> 同时：
> **财务说："上个月 LLM 费用涨了 3 倍。"**

### 3.2 大白话讲问题

客服处理一个投诉需要 20-30 轮对话。前 5 轮用户说清楚了：订单号 12345、用的京东快递、已经等了 7 天。

到了第 15 轮，LLM 已经忘了"京东快递"这个信息。为什么？因为每次调用 LLM 时，会把所有历史消息都传过去。30 轮对话 + 20 次工具调用的结果，合起来可能超过 2 万个 Token。超过 LLM 的上下文窗口后，最早的那些消息就被截断了。

原来的做法是：超过 3 轮就全部压缩成一句话。但压缩完连"订单号 12345"这种关键信息也丢了。

### 3.3 大白话讲思路

之前的压缩方式是一刀切——不管三七二十一，超过 3 轮就全部压成一坨。我的做法是分层处理：

```
1-3 轮：不压，保留全部
4-10 轮：只压工具返回的详细数据（JSON 太长），保留对话主线和关键信息
10 轮以上：让 LLM 主动总结一下前面说了什么
```

同时，我还把记忆按类型分了类。这样检索时不会把不相关的信息带进来。

### 3.4 代码实现流程

#### 第一步：对话轮数计算 + 可配置阈值

```python
# 阈值不是写死的，而是从配置中心读取
# 客服场景：低阈值（3/10），因为对话密集
# 财务场景：高阈值（5/15），因为对话轮次少但每轮信息量大
class MemoryConfig:

        self.level2_threshold = cfg["level2"]   # 超过这个轮数开始 L2 压缩
        self.level3_threshold = cfg["level3"]   # 超过这个轮数开始 L3 摘要
```

#### 第二步：三级压缩策略

```python
class HierarchicalCompressor:
    def __init__(self, config, chat_mdl):
        self.config = config
        self.chat_mdl = chat_mdl

    async def compress(self, messages):
        total_rounds = len([m for m in messages if m["role"] == "user"])
        
        # 先把 system prompt 单独拿出来，始终保留
        system_prompt = None
        if messages and messages[0]["role"] == "system":
            system_prompt = messages[0]
            rest = messages[1:]
        else:
            rest = messages

        # ─── Level 1：短对话，不压缩 ───
        if total_rounds <= self.config.level2_threshold:
            return messages  # 原样返回，零损失

        # ─── Level 2：中长度对话，只压工具详情 ───
        if total_rounds <= self.config.level3_threshold:
            compressed = []
            for msg in rest:
                if msg["role"] == "tool":
                    # 工具返回结果通常是冗长的 JSON，只保留前 200 字符
                    content = msg.get("content", "")
                    if len(content) > 200:
                        msg = {**msg, "content": content[:200] + "...[工具结果已压缩]"}
                compressed.append(msg)
            result = compressed
        else:
            # ─── Level 3：长对话，LLM 摘要 ───
            # 把早期历史交给 LLM 总结，保留最后一轮完整消息
            # 只保留了"关键信息"，去掉了重复的对话过程
            summary = await self.chat_mdl.async_chat(
                "总结以下对话的核心信息，包括：已解决的问题、用户的诉求、获取到的关键数据、待办事项。",
                rest[:-1]  # 不包括最后一轮
            )
            result = [
                {"role": "system", "content": f"[历史摘要] {summary}"},
                rest[-1]  # 保留最后一轮用户问题
            ]

        # 把 system prompt 放回开头
        if system_prompt:
            result.insert(0, system_prompt)
        return result

# 企业价值：
# - 3 轮以内零损失：短对话每条信息都重要，不压缩
# - 4-10 轮选择性压缩：200 字符保留工具结果摘要，LLM 知道"发生过什么"
# - 10 轮以上 LLM 摘要：早期细节被概括，但关键事实（订单号、诉求）被保留
```

#### 第三步：分类存储记忆（五类桶 + 批量分类）

```python
class StructuredMemory:
    """
    记忆按类型分 5 类存储：
    
    1. factual（事实）     ：客观信息，不会随时间改变
       → "用户是铂金会员，地址在北京"
    2. preference（偏好）  ：用户习惯，跨会话可用
       → "用户不喜欢客套，要直接答案"
    3. context（上下文）   ：本轮对话中发生的事情
       → "刚才查了订单 #12345，快递显示延期"
    4. session（会话状态） ：用户当前的情绪和态度
       → "用户今天催了 3 次，情绪不太耐烦"
    5. task_status（任务） ：待办事项和进度
       → "退款流程已完成，等待银行到账"
    """

    BATCH_SIZE = 5  # 初始值，后续可以根据对话长度动态调整

    def __init__(self, embedding_model):
        self.memories = {cat: [] for cat in ["factual", "preference", "context", "session", "task_status"]}
        self._pending = []  # 待分类的原始对话
        self._embedding_model = embedding_model
        self._memory_embeddings = {}  # 记忆内容 → embedding 向量

    async def add(self, user_input, response, chat_mdl):
        """添加对话到记忆队列，攒够 BATCH_SIZE 后批量分类"""
        self._pending.append({"user": user_input, "assistant": response})
        if len(self._pending) >= self.BATCH_SIZE:
            await self._batch_classify(chat_mdl)

    async def _batch_classify(self, chat_mdl):
        """批量分类积累的对话，一次 LLM 调用处理多条"""
        batch_text = "\n---\n".join(
            f"User: {p['user']}\nAssistant: {p['assistant']}"
            for p in self._pending
        )
        
        classification = await chat_mdl.async_chat(
            "分析以下对话，提取关键信息并按类型归类。\n"
            "类型说明：\n"
            "- factual: 客观事实（地址、会员等级、订单号）\n"
            "- preference: 用户偏好（喜欢的回答风格）\n"
            "- context: 本轮上下文（刚查了什么、说了什么）\n"
            "- session: 会话状态（用户情绪、催促次数）\n"
            "- task_status: 任务进度（退款到哪一步了）\n"
            "输出 JSON 格式：{\"factual\": [...], \"preference\": [...], ...}",
            [{"role": "user", "content": batch_text}]
        )

        try:
            parsed = json_repair.loads(classification)
            for category, items in parsed.items():
                if category in self.memories and items:
                    for item in items:
                        self.memories[category].append(item)
                        # 为记忆生成 embedding，用于后续语义检索
                        emb = await self._embedding_model.encode(str(item))
                        self._memory_embeddings[id(item)] = emb
        except Exception:
            logging.warning("记忆分类失败，跳过该批次——不影响正常对话")
        
        self._pending = []  # 清空队列

    async def get_relevant(self, query, top_k=3):
        """
        根据当前问题，检索最相关的 Top-K 条记忆
        
        不用全量拼接，只用 embedding 语义匹配
        """
        if not any(self.memories.values()):
            return ""

        query_emb = await self._embedding_model.encode(query)
        
        scored = []
        for category, items in self.memories.items():
            for item in items[-10:]:  # 只查每个分类最近 10 条，控制范围
                item_emb = self._memory_embeddings.get(id(item))
                if item_emb is not None:
                    score = cosine_similarity(query_emb, item_emb)
                    scored.append((score, category, item))

        scored.sort(key=lambda x: x[0], reverse=True)
        selected = scored[:top_k]

        parts = []
        for score, category, item in selected:
            parts.append(f"[{category}]({score:.2f}): {item}")
        return "\n".join(parts)

    def add_session(self, content):
        """添加本轮会话的临时记忆（不会落盘，对话结束即消失）"""
        self.memories["session"].append(content)
        if len(self.memories["session"]) > 5:
            self.memories["session"].pop(0)
```

#### 第四步：完整串联——一次请求中的压缩 + 检索流程

```
用户第 15 轮提问："退款到哪了？"
                  │
                  ▼
        ① 计算当前对话轮数 = 15
        ② 15 > 10 → 进入 Level 3 压缩
           ├── 把前 14 轮交给 LLM 做摘要
           └── 保留第 15 轮完整消息
                  │

        ③ 结构化记忆检索
           ├── 问题 "退款到哪了" → embedding 匹配
           ├── 命中 task_status → "退款流程已完成，等待到账"
           ├── 命中 context → "订单 #12345，京东快递，已等 7 天"
           └── 命中 factual → "用户是铂金会员，享受优先退款"

                  ▼
        ④ 最终注入 LLM 的上下文：
           [历史摘要]: 用户在询问订单 #12345 的退款进度...
           [task_status]: 退款流程已完成，等待到账

           第 15 轮用户问题: "退款到哪了？"
                  │
                  ▼
        ⑤ LLM 生成回答："您的订单 #12345 退款已完成"
```

### 3.5 对比：原来的方式 vs 现在的方式

| 场景 | 原来的方式 | 现在的方式 |
|------|-----------|-----------|
| 3 轮以内 | 全部压缩 → 丢失信息 | 不压缩 → 零损失 |
| 10 轮 | 还是压缩 → 关键信息丢了 | 只压工具详情 → 订单号等关键信息保留 |
| 20 轮 | Token 爆了 → 早期信息被截断 | LLM 摘要 → 关键事实保留 |
| 记忆检索 | 全量拼接 → 噪音信息多 | 语义 Top-3 → 精准匹配 |
| 分类成本 | 逐条分类 → LLM 调用频繁 | 批量分类 → 调用次数减少 |
| 场景适配 | 固定阈值 → 客服/财务都一样 | 可配置阈值 → 不同场景不同策略 |

### 3.6 面试官可能会追问

**问："3 轮和 10 轮这个阈值怎么定的？有理论依据吗？"**

> 没有特别严谨的理论依据，是从客服场景的对话数据里观察出来的。1-3 轮在聊同一个子问题，4-10 轮开始出现工具调用，10 轮以上 LLM 开始遗忘早期信息。关键是这个阈值不是写死的，我把它做成了可配置参数——客服场景用 3/10，财务场景用 5/15，不同场景可以调。

**问："5 条对话才分类一次，为什么是 5 条？有依据吗？"**

> 坦率说，5 条是一个初始值，不是经过严格调参得出的最优解。对话密集的客服场景 5 条可能太少（LLM 调用还是偏频繁），对话稀疏的财务场景 5 条又可能太多（好几天才攒够）。我的做法是把这个值做成了可配置参数，不同场景可以调。等积累足够多的线上数据后，再根据"LLM 调用成本 vs 记忆粒度"的权衡来调优。

**问："如果 LLM 摘要的时候丢掉了关键信息怎么办？"**

> 这个问题问得好。所以我在 Level 3 的摘要 prompt 里明确要求保留"订单号、金额、用户诉求"这类关键事实，并且在摘要完成后会做一次"关键信息一致性检查"——检查摘要是否包含了原始对话中的关键实体（订单号、快递公司、金额）。如果发现丢了，会触发补充摘要。当然这又会多一次 LLM 调用，所以是一个可选的增强，默认不开启。

Agent 用的所有工具都是写死在代码里的。这导致 3 个问题：

**问题 3：回滚慢**
v2 有 Bug 想回滚 v1？又得改代码、发版、重启。一轮下来 10 分钟过去了。

### 4.3 大白话讲思路

原来的做法：菜单印在墙上，想换菜得砸墙。
我的做法：菜单写在黑板上，想换菜擦了重写就行。

```
原来的模式：
  [代码里写死工具列表] → 改代码 → 发版 → 重启 → 用户断连
  
现在的模式：
  [Redis 里存工具信息] → 写入 Redis → Pub/Sub 通知 → Agent 下次请求自动加载
```

#### 第二步：动态加载工具（安全方式：importlib，非 pickle）

```python
class DynamicToolRegistry:
    """
    动态工具注册中心
    
    核心原则：
    1. 不存代码，只存类路径 → 安全（无 pickle 风险）
    2. 本地缓存版本号 → 减少 Redis 查询
    3. 变更只清除缓存，不中断当前请求 → 优雅
    """

    def __init__(self, redis):
        self.redis = redis
        self._local_cache: dict[str, type] = {}    # 工具名 → 类
        self._cache_version: dict[str, str] = {}    # 工具名 → 版本号

    async def load_for_agent(self):
        """Agent 启动时获取所有可用工具"""
        active_tools = await self.redis.smembers("agent_tools:active")
        
        tools = {}
        for name in sorted(active_tools):  # 排序保证顺序一致
            tool_cls = await self._load_tool(name)
            if tool_cls:
                tools[name] = tool_cls()
        return tools

    async def _load_tool(self, name):
        """加载单个工具（带缓存）"""
        # 1. 检查本地缓存是否最新
        cached_version = self._cache_version.get(name)
        remote_version = await self.redis.hget(f"agent_tool:{name}", "version")
        
        if name in self._local_cache and cached_version == remote_version:
            return self._local_cache[name]  # 缓存命中

        # 2. 缓存未命中或版本变了 → 从 Redis 重新加载
        meta = await self.redis.hgetall(f"agent_tool:{name}")
        if not meta:
            return None

        # 3. 用 importlib 安全加载（非 pickle，无远程代码执行风险）
        try:
            module_path, class_name = meta["class_path"].rsplit(".", 1)
            module = importlib.import_module(module_path)
            tool_cls = getattr(module, class_name)

            # 更新缓存
            self._local_cache[name] = tool_cls
            self._cache_version[name] = meta["version"]
            return tool_cls
        except (ImportError, AttributeError) as e:
            logging.error(f"加载工具 {name} 失败: {e}")
            return None
```

#### 第五步：后台监听 + 优雅缓存失效

```python
class ChangeListener:
    """
    后台任务：监听 Redis Pub/Sub 的工具变更消息
    
    设计要点：
    - 收到消息后不清除所有缓存，只清除受影响的那个工具
    - 不立即中断当前请求，只标记缓存为失效
    - 下次请求发现缓存版本号和 Redis 不一致，自动重新加载
    """

    def __init__(self, registry: DynamicToolRegistry):
        self.registry = registry

    async def start(self):
        pubsub = self.registry.redis.pubsub()
        await pubsub.subscribe("agent_tools:changes")
        
        async for message in pubsub.listen():
            if message["type"] != "message":
                continue
            
            tool_name = message["data"].decode()
            # 只清除这一个工具的缓存，不是全部清除
            self.registry._local_cache.pop(tool_name, None)
            self.registry._cache_version.pop(tool_name, None)
            logging.info(f"工具缓存已清除: {tool_name}，下次请求将加载最新版本")
            # 当前正在执行的请求不受影响，它持有的还是旧的工具引用
```

### 4.5 对比：原来的方式 vs 现在的方式

| 操作 | 原来 | 现在 |
|------|------|------|
| 新增工具 | 改代码→发版→重启→断连 2min | 改 Redis 配置→通知→重启生效 |
| 工具升级 | 改代码→发版→重启 | 改配置→通知→重启 |
| 回滚 | 又一轮改代码→发版→重启 | 改配置→通知→重启 |
| 安全风险 | pickle 反序列化高危 | importlib 路径受限安全 |
| 代码耦合 | 工具列表硬编码在 Agent 代码中 | Agent 代码与工具配置解耦 |

### 4.6 面试官可能会追问

**问："为什么不用 pickle 序列化？"**

> 这是安全考虑。Pickle 反序列化时可以执行任意代码。如果 Redis 被攻破，攻击者在 Redis 里放一个恶意 pickle 数据，Agent 反序列化时就会执行攻击者的代码——相当于把服务器权限送出去了。Importlib 只能在 Python 的 `sys.path` 下导入模块，安全得多。而且 pickle 还有兼容性问题——工具类改了代码后旧的 pickle 数据反序列化会失败。

**问："如果 Agent 正在执行一个请求，你突然升级了工具，会不会出问题？"**

> 不会。Agent 实例初始化完成后，它持有的工具引用就是固定的。当前请求会继续用旧版本执行完。执行完毕后，ChangeListener 收到通知清除缓存，下一个请求来的时候自动从 Redis 加载新版本。整个过程对用户无感。

**问："Pub/Sub 消息丢了怎么办？Agent 没收到通知不就一直用旧版？"**

> 不只依赖 Pub/Sub。Agent 每次请求时还会检查本地缓存的版本号是否和 Redis 一致。如果发现不一致（比如 Pub/Sub 消息丢了），也会重新加载。Pub/Sub 是用来"加速通知"的，不是唯一渠道。版本号比对是兜底。

**问："你说多版本共存 + active 指针回滚太复杂没做，那版本冲突怎么处理的？"**

> 我的做法很简单：每个工具在 Redis 里只存一份配置，版本号只是用于缓存比对。新版本直接覆盖旧配置。如果新版本有问题，用 Git 回滚代码 + 修改 Redis 配置指向旧版本。这听起来没有"秒级回滚"酷，但对一个 5-10 个工具的项目来说够用了。哪天工具数量到了 50+，升级确实频繁了，再上多版本方案不迟。

```
  ↓ 运营还说"你查到了但链接是空的"（另一个工程问题推动）
第五版：结果校验 → 空结果自动重试
  ↓ 客服说"之前说过的它又忘了"（新场景推动）
第六版：三级压缩 + 结构化记忆 → 长对话优化
  ↓ 开发说"每次加个工具都要重启被骂了"（运维问题推动）
第七版：动态装配 → Redis 热加载
```

### 5.2 核心原则

每个改造点的开头都是：**"后来遇到了一个问题……"**

面试官听完会觉得你不是在背技术方案，而是在讲一个真实的故事。这个故事里的每一个改动都有前因后果，不是拍脑袋想出来的。
